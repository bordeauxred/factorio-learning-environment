# Minimap and combined observation profile — 2026-09-18

Configuration: 14×128×128 float32 minimap, four tiles per cell, 512×512 world tiles. Four minimap chunk samples per poll; narrow buildability retains 63×128×128 and a 256-check budget. Base Factorio 2.0.73 under Docker/box64; macOS-26.3.1-arm64-arm-64bit-Mach-O.

The world is paused with 1,000 iron chests, one tracked character, and generated natural terrain beyond the flattened central 128×128 tiles. Visibility uses generated terrain, matching the existing FLE terrain stream. The minimap is fully populated before steady-state measurements; buildability is progressively filling. Each mode has 20 warmup polls and 100 measured polls. No GPU transfer or model execution is included.

## Polling through owned training samples

| Mode | Total median | Total p95 | Client median | Client p95 | Median payload |
|---|---:|---:|---:|---:|---:|
| minimap_only | 4.603 ms | 6.637 ms | 0.123 ms | 0.173 ms | 85 bytes |
| narrow_only | 4.339 ms | 6.329 ms | 0.764 ms | 1.547 ms | 77 bytes |
| combined | 7.032 ms | 9.270 ms | 1.474 ms | 1.925 ms | 163 bytes |
| minimap_only_repeat | 4.732 ms | 5.982 ms | 0.132 ms | 0.214 ms | 85 bytes |

Total includes RCON, Lua sampling, decoding, observation assembly and copying stable float32 training arrays. Client excludes RCON/Lua. Narrow means the existing context grid, globals, nearest-entity table/mask and narrow buildability. It does not mean reducing the existing 288-tile context grid to 128 tiles. Combined uses one RCON round trip. A final standalone minimap run brackets the experiment.

Unchanged chunks still get resampled but transmit timestamps instead of full chunk values. This paused-world workload measures that steady polling path; moving units and world edits can increase payload/decoding costs. Chunk budgets do not cap entity density or Lua execution time.

## CPU-only sample creation

| Mode / operation | Median | p95 |
|---|---:|---:|
| minimap_only / minimap_copy | 0.033 ms | 0.054 ms |
| narrow_only / narrow_sample | 0.461 ms | 0.572 ms |
| combined / minimap_copy | 0.012 ms | 0.022 ms |
| combined / narrow_sample | 0.365 ms | 0.443 ms |
| combined / combined_sample | 0.382 ms | 0.447 ms |
| minimap_only_repeat / minimap_copy | 0.033 ms | 0.045 ms |

`minimap_copy` copies all map channels and sample ticks. `narrow_sample` assembles the entity view and copies the base arrays, casts all buildability values to float32, and copies its ticks. `combined_sample` does both.

## Initial fill and memory

| Mode | Fill polls | Elapsed | Median fill poll | p95 fill poll |
|---|---:|---:|---:|---:|
| minimap_only | 64 | 347.0 ms | 4.928 ms | 9.202 ms |
| combined | 64 | 342.6 ms | 5.121 ms | 7.645 ms |
| minimap_only_repeat | 64 | 334.3 ms | 5.027 ms | 6.956 ms |

Initial fill is minimap-only acquisition, outside the steady timers and with buildability disabled. At the fixed benchmark origin, 256 chunks fill in 64 polls. An origin not aligned to 32 tiles overlaps up to 289 chunks and needs at least 73 polls at budget four. Dirty work can increase those counts.

An owned minimap sample uses exactly **1 MiB**: 917,504 bytes for float32 values and 131,072 bytes for int64 per-cell timestamps. The combined sample is approximately **5.96 MiB**, including the previous narrow sample. Python object overhead is excluded. The live minimap decoder also retains roughly 0.81–0.92 MiB of chunk arrays for scrolling, in addition to its dense output.
