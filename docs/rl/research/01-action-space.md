# V0 macro-action space: code-grounded research

Scope: this is a static reading of `feat/pufferlib-rl`; no live Factorio process was queried. The current Gym action remains a Python `code: str`, executed through `instance.eval`, and a step gathers fresh entities, player inventory, and research state afterward (`fle/env/gym_env/action.py:8-13`, `fle/env/gym_env/environment.py:307-325`, `fle/env/gym_env/environment.py:446-449`). **One Python tool invocation is not necessarily one RCON round trip or one atomic game action**: the common `execute` wrapper sends an RCON command, while several client methods call other tools or poll RCON (`fle/env/tools/controller.py:207-215`, `fle/env/tools/agent/move_to/client.py:37-69`, `fle/env/tools/agent/connect_entities/client.py:57-69`).

## 3. Anchor-relative placement

`place_entity` accepts a world `Position`, with an `exact` switch; it has no anchor/entity parameter. `exact=False` searches around the supplied world target up to radius 10, so it loses precise offset semantics (`fle/env/tools/agent/place_entity/client.py:19-33`, `fle/env/tools/agent/place_entity/server.lua:246-283`). `place_entity_next_to` accepts a **`reference_position`, not a `reference_entity` pointer**, plus a cardinal `direction` and integer `spacing`. Lua finds an entity intersecting a small box around that position, uses its oriented `tile_width`/`tile_height`, adds half the two footprints plus gap, then rounds each coordinate upward to a half tile (`fle/env/tools/agent/place_entity_next_to/client.py:12-26`, `fle/env/tools/agent/place_entity_next_to/server.lua:165-170`, `fle/env/tools/agent/place_entity_next_to/server.lua:179-230`). It can silently pick an alternative site/orientation for inserters, chests, belts, and pole collisions, so it is **not** an exact `(dx,dy)` primitive (`fle/env/tools/agent/place_entity_next_to/server.lua:320-378`).

For the proposed `PLACE=(prototype, anchor_entity, dx, dy, direction)`, **`place_entity` with `exact=True` is the better substrate**. The adapter should resolve the current anchor position, add `(dx,dy)` in world coordinates, normalize to a valid center grid for the selected entity footprint, and pass `Position(anchor.x+dx, anchor.y+dy)` and desired orientation. Its result should be checked against the requested target, because an offshore pump forces non-exact placement (`fle/env/entities.py:273-312`, `fle/env/tools/agent/place_entity/client.py:19-26`, `fle/env/tools/agent/place_entity/server.lua:193-204`, `fle/env/tools/agent/place_entity/server.lua:372-400`). Integer `dx,dy ∈ [-8,8]` are representable as Python float coordinates, **but not guaranteed buildable or reachable**; `place_entity` enforces player reach and `surface.can_place_entity`, and multi-tile entities need their entire oriented footprint free (`fle/env/entities.py:273-275`, `fle/env/tools/agent/place_entity/server.lua:120-149`, `fle/env/tools/agent/place_entity/server.lua:207-229`, `fle/env/mods/utils.lua:104-112`). The entity model carries live `tile_dimensions`, but no static Python footprint table for all prototypes; Lua's `place_entity_next_to` uses runtime dimensions and half-tile rounding. Exact parity/center rules for every prototype are **UNVERIFIED** without live prototype data (`fle/env/entities.py:521-529`, `fle/env/tools/agent/place_entity_next_to/server.lua:183-228`).

## 4. Masking sources and round-trip costs

Cost notation: **0 extra** means a fresh field already exists in the held Gym observation; **+1 RCON** means one additional `Tool.execute` or direct `send_command`; compound tools can cost more. The current Gym observation itself calls `get_entities`, `inspect_inventory`, and `_save_research_state`, and its `get_entities` wrapper includes a 0.1-second client sleep. The tiered diff scenario emits entity inventory rows and terrain records but has a 47-tick reconciliation period and quantized emission triggers; stale or absent data cannot prove a placement is valid (`fle/env/gym_env/environment.py:307-325`, `fle/env/tools/agent/get_entities/client.py:85-95`, `fle/cluster/scenarios/open_world/observation_diff.lua:18-46`).

| Op | Source for a useful conditional mask; extra cost; cheaper derivation |
|---|---|
| `WAIT` | Duration is adapter policy, not a world-validity predicate. Held speed/tick fields exist, but they are based on `storage.elapsed_ticks`; `sleep` is an RCON counter update plus a speed-adjusted wall-clock sleep, **not exact simulation stepping** (`fle/env/gym_env/environment.py:322-326`, `fle/env/tools/agent/sleep/client.py:37-53`, `fle/env/tools/agent/sleep/server.lua:1-9`). |

## 5. Invalid-action behaviour

There is **no uniform invalid-action contract**. Python validation can raise `AssertionError`, `ValueError`, or generic `Exception`; Lua errors are converted by `pcall` into response strings, and `Controller.execute` can turn unforeseen exceptions into `{}`. Some tools return `False`, `None`, `[]`, or an unchanged target instead of raising (`fle/env/tools/controller.py:207-215`, `fle/env/tools/controller.py:236-293`, `fle/env/tools/agent/can_place_entity/client.py:24-45`, `fle/env/tools/agent/get_entity/client.py:55-59`, `fle/env/tools/agent/insert_item/client.py:59-87`). Inside the Python-program REPL, a top-level exception is caught, logged, stops the remaining statements, increments a counter, and restores a *shallow copy* of previously successful Python variables. The Gym step receives a text result; its `error_occurred` test is a string search, and `error_penalty` defaults to 0.0 and is subtracted regardless of that flag (`fle/env/namespace.py:1108-1164`, `fle/env/gym_env/environment.py:230-240`, `fle/env/gym_env/environment.py:446-474`). A dedicated RL adapter needs its own structured success/failure classification and penalty rule (`fle/env/gym_env/environment.py:450-451`, `fle/env/gym_env/environment.py:474`).

**Ticks are not guaranteed zero on invalid actions.** Validation before a Lua mutation can fail without adding synthetic `storage.elapsed_ticks`, but the server is unpaused during a Gym step, so actual `game.tick` may advance during RCON latency. Some failures happen *after* mutation or synthetic tick addition: crafting increments elapsed ticks before inventory-space validation; `shift_entity` picks up first; `place_entity_next_to` creates before its alleged inventory check (which calls `can_insert`, a capacity check, then `remove`, without verifying ownership); and `set_research` cancels prior research before `add_research` can fail. Namespace rollback does **not** roll back game-side effects; a cached entity pointer may therefore become stale. Exact actual ticks consumed by a given failure are **UNVERIFIED** from static code (`fle/env/gym_env/environment.py:433-449`, `fle/env/tools/agent/craft_item/server.lua:161-173`, `fle/env/tools/agent/shift_entity/client.py:37-70`, `fle/env/tools/agent/place_entity_next_to/server.lua:533-554`, `fle/env/tools/agent/set_research/server.lua:34-39`, `fle/env/namespace.py:1158-1164`). Masking should remove clear impossibilities, while the adapter must still tolerate and re-observe after failed tool calls (`fle/env/gym_env/environment.py:497-521`).

## 6. Time advancement

The default `FactorioInstance` is `fast=True`, `reset_speed=10`, `reset_paused=False`; Gym registry explicitly starts at speed 10, and server config has `auto_pause=false`. `GameControl` writes `game.speed` and `game.tick_paused` via RCON. Gym's default `pause_after_action=True` unpauses at the start of `step`, performs the Python action and several observation/score queries, then pauses at the end. Consequently the simulation **free-runs at configured speed during the step**, and wall-clock RCON/observation latency changes actual game ticks (`fle/env/instance.py:186-220`, `fle/env/instance.py:66-103`, `fle/env/gym_env/registry.py:137-145`, `fle/env/gym_env/registry.py:184-193`, `fle/cluster/config/server-settings.json:39-41`, `fle/env/gym_env/environment.py:433-449`, `fle/env/gym_env/environment.py:497-521`). Pausing/unpausing exists; an API that advances **exactly N actual `game.tick` ticks** is **UNVERIFIED** in the reviewed environment/cluster code—no such call was found in the timing control, Gym step, or `sleep` implementation (`fle/env/instance.py:66-143`, `fle/env/gym_env/environment.py:417-523`, `fle/env/tools/agent/sleep/server.lua:1-9`).

Crucially, `get_elapsed_ticks()` reads **`storage.elapsed_ticks`, not `game.tick`**. Fast-mode movement/harvest/crafting add estimated ticks to that counter; `sleep(seconds)` adds `seconds*60` to it, returns `game.tick` but ignores that value in Python, then sleeps for `added_ticks/60/game_speed` real seconds. It does not command the simulation to run N ticks. When paused, its counter can advance without the factory advancing; when unpaused, the factory advances according to real scheduling, not exactly the requested duration. `sleep` has no implemented 15-second cap despite its docstring (`fle/env/instance.py:124-135`, `fle/env/tools/agent/move_to/server.lua:171`, `fle/env/tools/agent/harvest_resource/server.lua:369-370`, `fle/env/tools/agent/craft_item/server.lua:161-168`, `fle/env/tools/agent/sleep/client.py:31-53`, `fle/env/tools/agent/sleep/server.lua:1-9`). The Gym observation's tick/time and response `ticks` inherit this synthetic counter, so they cannot be treated as authoritative simulation time (`fle/env/gym_env/environment.py:322-326`, `fle/env/gym_env/environment.py:481-490`). **`WAIT(duration)` is implementable only as approximate wall-time waiting under the present API, not deterministic N-tick stepping; reproducible episodes at exact tick granularity are UNVERIFIED** (`fle/env/tools/agent/sleep/client.py:37-53`, `fle/env/gym_env/environment.py:436-449`).

## 7. Top five V0 risks

1. **Fixed full-size vocabularies cannot be justified from repo snapshots.** The 142-value `Prototype` enum includes aliases and nonentities; the 212-recipe snapshot lacks categories/unlock data; 60 distinct `Technology` enum values are not the complete live force catalogue. Inventory item keys and techs come from live game state. A startup, sorted, versioned prototype export or a deliberately restricted V0 allowlist is required (`fle/env/game_types.py:83-113`, `fle/env/game_types.py:304-305`, `data/recipes/recipes.lua:1-18`, `data/recipes/main.py:23-26`, `fle/env/entities.py:170-217`, `fle/env/tools/admin/save_research_state/server.lua:56-59`).
2. **One macro tool call can mean many RCON calls and non-atomic mutations.** `move_to` requests/polls a path; `connect_entities` refreshes entities, reads inventory and attempts paths; belt insert and group pickup loop. Per-step latency and partial success vary by op and state (`fle/env/tools/agent/move_to/client.py:37-69`, `fle/env/tools/agent/connect_entities/client.py:448-486`, `fle/env/tools/agent/connect_entities/client.py:508-588`, `fle/env/tools/agent/insert_item/client.py:41-70`, `fle/env/tools/agent/pickup_entity/client.py:36-71`).
3. **Exact masks need information the held observation does not fully supply.** Craft/recipe categories, machine compatibility, prototype fuel/module metadata, and exact surface placement require runtime properties. Exhaustive `can_place_entity` probing is an RCON call per candidate and can teleport the player; dry-run connection routing is compound (`fle/env/tools/agent/craft_item/server.lua:79-109`, `fle/env/tools/agent/set_entity_recipe/server.lua:8-37`, `fle/env/tools/agent/insert_item/server.lua:67-161`, `fle/env/mods/utils.lua:115-131`, `fle/env/tools/agent/get_connection_amount/client.py:29-32`).
4. **`PLACE` geometry and direction heads need narrower semantics.** `place_entity_next_to` handles oriented footprints but may relocate automatically; `place_entity` is exact world-position based and offshore pumps force inexact mode. Direction enum has 8 values whereas some servers accept only 4. A single unrestricted `dx,dy,direction` mask would misrepresent these tools (`fle/env/tools/agent/place_entity_next_to/server.lua:179-230`, `fle/env/tools/agent/place_entity_next_to/server.lua:320-378`, `fle/env/tools/agent/place_entity/server.lua:193-204`, `fle/env/entities.py:249-260`, `fle/env/tools/agent/rotate_entity/server.lua:36-40`).
5. **Tick determinism and failure recovery are not provided by the current step boundary.** `sleep` updates a synthetic counter and waits in real time; Gym unpauses through action and observation work. Invalid operations can mutate world state before raising, while REPL rollback only restores Python bindings. An RL layer needs explicit real-tick accounting, a stepping mechanism if exact-time training is required, and post-error resynchronization (`fle/env/tools/agent/sleep/server.lua:1-9`, `fle/env/gym_env/environment.py:436-449`, `fle/env/gym_env/environment.py:497-521`, `fle/env/tools/agent/shift_entity/client.py:37-70`, `fle/env/namespace.py:1128-1164`).
