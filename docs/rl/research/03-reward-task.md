## 1. Task system

`TaskABC` stores `trajectory_length`, `starting_inventory`, goal text, task key, an all-research flag, and optional per-agent instructions. It is a conventional base class, not a Python `ABC` with abstract methods: `verify` and `setup_instance` are `pass`, and `enhance_response_with_task_output` returns the unchanged response. `setup` installs the inventory and research policy, resets the instance, runs `setup_instance`, then snapshots `GameState` (`fle/eval/tasks/task_abc.py:8-23`, `fle/eval/tasks/task_abc.py:25-33`, `fle/eval/tasks/task_abc.py:35-68`). The base `verify(score, step, instance, step_statistics)` signature includes `step`, while concrete `ThroughputTask.verify` and its Gym call omit it; this is an interface inconsistency, though that Gym call matches the concrete method (`fle/eval/tasks/task_abc.py:35-49`, `fle/eval/tasks/throughput_task.py:67-69`, `fle/env/gym_env/environment.py:455-459`). `DefaultTask` starts empty, leaves research locked, and always returns `TaskResponse(success=False, meta={})`; `UnboundedThroughputTask` can vary starting inventory and research, but its verification also always reports `success=False` and only returns achievement metadata (`fle/eval/tasks/default_task.py:15-28`, `fle/eval/tasks/unbounded_throughput_task.py:33-48`, `fle/eval/tasks/unbounded_throughput_task.py:50-75`). The registry also contains `open_play` and `open_play_production`; the latter has no `TaskABC` class mapping and is handled by Inspect (`fle/eval/tasks/task_definitions/unbounded/unbounded_tasks.py:124-155`, `fle/eval/tasks/task_definitions/task_registry.py:57-66`).

`ThroughputTask` sets `throughput_entity`, integer `quota`, and `holdout_wait_period`; its default starter inventory contains 500 coal, 50 burner drills, 10 stone furnaces, many electric machines and connections, and it unlocks **all** technology (`fle/eval/tasks/throughput_task.py:9-31`, `fle/eval/tasks/throughput_task.py:37-65`). In `verify()`, the configured pre-holdout sleep is commented out. It repeatedly evaluates `sleep(holdout_wait_period)`, reads `achievements["dynamic"].get(target, 0)`, retains the maximum **strictly increasing** window, and stops at the first non-increase. It returns `TaskResponse(success=(max >= quota), meta={"<target> achieved throughput per <period> seconds": max, REWARD_OVERRIDE_KEY: max})`; it does not return a rate in items/minute if the period is changed from 60 seconds, nor does it use the supplied score or statistics (`fle/eval/tasks/throughput_task.py:63-93`). `max_achievements` is tracked but not returned (`fle/eval/tasks/throughput_task.py:70-92`). The Gym wrapper calls `verify` after every action, terminates on its `success`, and uses that maximum as the **whole step reward**, even on failure; `truncated` remains false (`fle/env/gym_env/environment.py:446-474`, `fle/env/gym_env/environment.py:519-523`). This is not the proposed reward.

The Gym registry discovers every key, calls `gym.register(id=task_key, entry_point=...make_factorio_env, kwargs={"spec": spec})`, and auto-registers on import. Hence the IDs are bare task keys such as `iron_ore_throughput`, without a `-v0` suffix; `make_factorio_env` then builds a live instance and calls `task.setup` (`fle/eval/tasks/task_factory.py:8-20`, `fle/eval/tasks/task_definitions/task_registry.py:43-65`, `fle/eval/tasks/task_definitions/task_registry.py:89-119`, `fle/env/gym_env/registry.py:36-83`, `fle/env/gym_env/registry.py:112-113`, `fle/env/gym_env/registry.py:184-193`, `fle/env/gym_env/registry.py:234-235`). Discovery includes `open_play_production` even though `TaskRegistry.create_task` will reject its type: being listed as an ID does not establish constructibility (`fle/eval/tasks/task_definitions/task_registry.py:51-66`, `fle/eval/tasks/task_definitions/task_registry.py:112-119`, `fle/env/gym_env/registry.py:47-54`).

## 3. Recipe dependency graph

`data/recipes/recipes.lua` is a Lua literal **list of pairs**: `{"recipe-name", {{ {amount=..., name=..., type="item"|"fluid", ...}, ... }}}`. Its `electronic-circuit` entry is, verbatim (whitespace compacted), `{"electronic-circuit", {{{amount = 1, name = "iron-plate", type = "item"}, {amount = 3, name = "copper-cable", type = "item"}}}}` (`data/recipes/recipes.lua:988-1004`). Some ingredients have `catalyst_amount`, e.g. coal liquefaction's heavy oil (`data/recipes/recipes.lua:3821-3842`). The repository's offline converter already decodes the Lua with `slpp`, maps recipe name to the first nested ingredient list, and recursively builds an ingredient tree, stopping on visited nodes (`data/recipes/main.py:1-26`, `data/recipes/main.py:29-65`). This can build an **ingredient-recipe dependency graph offline without a game**. It cannot establish the **full product dependency graph**: recipe key is not always the product name (`basic-oil-processing`, `coal-liquefaction`, `uranium-processing`, fill/empty barrel), and there are no result names or counts in these entries (`data/recipes/recipes.lua:3792-3842`, `data/recipes/recipes.lua:3844-3861`, `data/recipes/recipes.lua:4047-4069`, `data/recipes/recipes.lua:4138-4147`). There is also no `result_count`, `energy`/crafting time, category, `enabled`, or enabling technology field in the snapshot's entry structure (`data/recipes/recipes.lua:988-1004`, `data/recipes/main.py:23-26`). Thus exact per-unit material unrolling and machine sizing are **UNVERIFIED** offline. `get_prototype_recipe` queries `player.force.recipes[recipe_name]` live; the server serializer supplies ingredients, **products with amount/type/probability**, category, `enabled`, and energy, but the Python client constructs a `Recipe` using only ingredients and products, discarding the serialized category/energy/enabled fields despite the model having them (`fle/env/tools/agent/get_prototype_recipe/server.lua:1-8`, `fle/env/mods/serialize.lua:573-611`, `fle/env/tools/agent/get_prototype_recipe/client.py:35-53`, `fle/env/entities.py:484-500`). Enabling *technology identity* is not in that serializer; a live technology-effects traversal (already used by `craft_item`) can find `unlock-recipe`, while the research-state tool supplies technology state/prerequisites but not those effects (`fle/env/tools/agent/craft_item/server.lua:64-76`, `fle/env/tools/admin/save_research_state/server.lua:19-44`, `fle/env/tools/admin/save_research_state/server.lua:56-59`). With product edges and recycling, strongly connected components or explicit catalyst/net-flow handling are required; the ingredient-only snapshot is insufficient to determine all net yields (`data/recipes/recipes.lua:3821-3842`, `data/recipes/recipes.lua:3844-3861`, `data/recipes/recipes.lua:4047-4069`, `data/recipes/recipes.lua:4138-4179`, `fle/env/mods/serialize.lua:594-610`). ## 4. Concrete potential for a restricted item tree

For a V0 item whose recipe key equals its sole intended product, choose one recipe per item, traverse **backwards** from target `q` through ingredient names, stop at raw leaves, deduplicate names, and include `q` itself. I call this `Ancestors⁺(q)` because ordinary “ancestors” would exclude `q`; excluding it would omit direct reward for target inventory/rate. Reject cycles rather than silently interpreting the converter's visited-node truncation as a valid bill of materials (`data/recipes/main.py:29-52`, `data/recipes/recipes.lua:989-1004`). For each included item set `d_i` to its **shortest edge distance from `q`**, and `w_i = 2^{-d_i}/Σ_j 2^{-d_j}`. This is explicit, positive, sums to one, and puts more weight near the target. A unit-requirement weight could be economically better, but this snapshot lacks output counts and alternate-product routing; depth weights are the honest offline V0 choice (`data/recipes/recipes.lua:988-1004`, `fle/env/mods/serialize.lua:594-610`).

Use `α=1/2`. For a quota `Q` per minute, initialize **design** normalizers `n̄_i=Q` items and `ρ̄_i=Q` automatically produced items/minute for all included items; `Q=16` for the existing electronic-circuit target. These are reward scales, **not** a claim that 16 copper cables/min feeds 16 circuits/min. A later prototype-complete export could replace them with target-rate input requirements, accounting for output counts, probability and byproducts (`fle/eval/tasks/task_definitions/lab_play/throughput_tasks.py:81-86`, `data/recipes/recipes.lua:989-1004`, `fle/env/mods/serialize.lua:594-610`). Keep denominators fixed for an entire training/evaluation run, and cap each input to `4Q` before taking logs to bound terminal residuals. Define `n_i` as an authoritative, deduplicated count in player and force-owned container/machine inventories, excluding map resource patches; define `ρ_i` from **automatic** production counter deltas over elapsed true simulation time, with the rate-window/EMA state included in the RL state. This is a proposed instrumentation contract: current Gym observation reads player inventory and entity representations separately, not an authoritative global stock total (`fle/env/gym_env/environment.py:307-334`, `fle/env/tools/agent/inspect_inventory/server.lua:9-17`, `fle/env/tools/agent/inspect_inventory/server.lua:56-78`). For items that can be hand crafted or mined, subtract the recorded manual flows as in the existing dynamic-achievement calculation (`fle/env/utils/achievements.py:18-40`, `fle/env/tools/agent/craft_item/server.lua:112-127`, `fle/env/tools/agent/harvest_resource/server.lua:8-18`).

## 5. Throughput measurement

The existing holdout uses **dynamic achievements**, not a rate estimator: `eval_program_with_achievements` snapshots `ProductionFlows`, executes `sleep(period)`, snapshots again, and `calculate_achievements` subtracts manually harvested/crafted outputs from produced-output deltas (`fle/env/utils/achievements.py:7-40`, `fle/env/utils/achievements.py:43-63`, `fle/eval/tasks/throughput_task.py:75-92`). The Lua stats endpoint returns cumulative `input`/`output` and manual records, for items and fluids; its local variable names are confusing, but FLE's scorer explicitly treats Factorio `input_counts` as produced and `output_counts` as consumed, and the endpoint maps those to `ProductionFlows.output` and `.input` respectively (`fle/env/tools/admin/get_production_stats/server.lua:10-39`, `fle/env/tools/agent/score/server.lua:1-11`). `ProductionFlows` itself stores dictionaries/lists and computes positive **deltas**; it has no EMA, rolling window or timestamps (`fle/commons/models/achievements.py:14-39`, `fle/commons/models/achievements.py:56-79`). A cheap RL-step estimate can reuse the beginning/end counter reads already in `FactorioGymEnv.step` and compute `60 × Δautomatic_output(q)/Δtrue_game_seconds`; use the positive dynamic difference, not net inventory changes, to avoid confusing consumption with production (`fle/env/gym_env/environment.py:440-443`, `fle/env/gym_env/environment.py:476-490`, `fle/env/utils/achievements.py:27-40`). Keep a ring buffer of `(true game tick, cumulative automatic count)` or update an EMA only when true simulated time advances, and expose both count and elapsed window. The present `ProductionFlows` model alone cannot supply an EMA (`fle/commons/models/achievements.py:14-39`).

The configured holdout is 60 nominal game seconds, but `verify` tries **at least two** such windows (second must fail to exceed the first), potentially more while counts rise, after **every** action; pre-holdout is commented out. It therefore changes the factory between agent decisions, introduces a large and variable measurement delay, and returns the *best* recent window rather than current steady throughput (`fle/eval/tasks/throughput_task.py:70-93`, `fle/env/gym_env/environment.py:446-464`). `sleep` adds `seconds×60` to `storage.elapsed_ticks` and then waits approximate real time according to speed; it does not command an exact number of `game.tick` simulation ticks (`fle/env/tools/agent/sleep/server.lua:1-9`, `fle/env/tools/agent/sleep/client.py:37-51`). **Actual** holdout duration in simulation ticks is therefore **UNVERIFIED** without a true-tick read. Do not run `verify()` per RL step; use counter-delta shaping during rollout, and a single final validation window after a fixed warm-up for success. One-minute throughput from a one-second window has severe integer noise: a single item is 60/min, while a 16/min line has mean spacing 3.75 seconds; a ten-second window still changes in 6/min increments. Those are arithmetic consequences of the configured quota/window (`fle/eval/tasks/task_definitions/lab_play/throughput_tasks.py:81-86`, `fle/eval/tasks/task_definitions/lab_play/throughput_tasks.py:45-47`), not measured FLE variance. Machine batching, startup latency, and supply blockage add further variance; magnitudes are **UNVERIFIED**. An EMA may smooth shaping, but terminal success should require the actual 60-second automatic count, never an EMA threshold.

## 6. Reward hacking and what potential shaping guarantees

With **the same transition discount** `β_t=γ^(Δt/τ)` in both the RL return and `F_t=β_tΦ(s_{t+1})−Φ(s_t)`, discounted shaping telescopes pathwise to `−Φ(s_0)+[Π_{k<T}β_k]Φ(s_T)`. For a discounted infinite-horizon Markov objective with bounded potential, the last term vanishes, so the shaping does not change optimal policies. The fixed cap above makes `Φ` bounded. In a finite episode the residual is **not zero** unless `Φ(terminal)=0` (or the boundary correction is applied); maximizing terminal stock can change the policy. The time-cost term does **not by itself** invalidate the theorem if it is part of the same discounted base reward, but different discount conventions, artificial truncation, and terminal scoring do. A windowed/EMA `ρ_i` is not a function of the **instantaneous factory snapshot** alone: the counter history, last timestamp, and EMA accumulator must be in the Markov state. If those are hidden, a state-only policy-invariance claim does not apply, although telescoping still holds over fully specified trajectories. FLE's Gym wrapper currently uses a per-step quota override and terminates on `TaskResponse.success`, with no horizon truncation; it does not implement this shaping/discount contract (`fle/env/gym_env/environment.py:453-474`, `fle/env/gym_env/environment.py:519-523`).

| Concrete exploit against the proposed `Φ` | Why it pays / code evidence | Mitigation; does the theorem suffice? |
|---|---|---|
| **Craft then destroy, or manually craft a circuit and dump it just before cutoff.** `n_q` and possibly raw production counters rise even if no automatic factory exists; manual crafting updates production statistics (`fle/env/tools/agent/craft_item/server.lua:112-127`, `fle/env/tools/agent/craft_item/server.lua:186-203`). | Count only automatic rate for `ρ`, require terminal 60-second automatic production, and set terminal `Φ=0`. **Finite-horizon residual needs explicit fix**; full infinite-horizon telescoping alone would cancel a complete loop (`fle/env/utils/achievements.py:18-40`). |
| **Insert/extract the same plates between player and chest or furnace.** If `n` is read from only one location, a transfer looks like creation; FLE has insert and extract paths (`fle/env/tools/agent/insert_item/server.lua:260-266`, `fle/env/tools/agent/extract_item/server.lua:170-194`). | Deduplicate and aggregate inventories, or use production counters for progress. **Explicit measurement fix**; a potential over a wrongly observed partial state is not a valid factory-state potential. |
| **Stockpile a cheap ancestor indefinitely.** A chest of iron ore raises its `ln(1+n)` term while circuits stay at zero; 40 ore already yields `0.062416` in the worked example (`data/recipes/recipes.lua:989-1004`, `data/recipes/recipes.lua:1715-1724`). | Keep the `4Q` stock cap, small leaf weight, terminal `Φ=0`, and require target throughput. **Explicit finite-horizon fix**; the infinite-horizon theorem only removes the incentive if its conditions hold. |
| **Hand-mine ore forever.** The mining tool inserts mined items into player inventory and records them as harvested, so stock rises even though automatic ore rate should be zero (`fle/env/tools/agent/harvest_resource/server.lua:8-18`, `fle/env/tools/agent/harvest_resource/server.lua:373-380`). | Exclude harvested counts from `ρ`; cap `n`; charge true game time and steps; gate leaf stock reward on an operating downstream chain if empirical farming persists. **Explicit fix** for finite training; a potential can still misdirect learning even when asymptotically invariant. |
| **Build many idle machines.** The populated task gives 50 drills and 10 furnaces; a naive “built capacity” surrogate would score them without output (`fle/eval/tasks/throughput_task.py:9-31`). | The specified `Φ` has **no machine-count term**, so idle machines alone yield zero shaping. Keep it that way; verify actual output. **No theorem needed** for this specific exploit. |
| **Fill one giant chest with intermediate copper cable, gaming a moving normalizer.** If `n̄_i` is recomputed from agent stock or observed maxima, the agent can manipulate scale; copper cable is a direct circuit ingredient (`data/recipes/recipes.lua:989-1004`). | Freeze `n̄_i=Q`, `ρ̄_i=Q` per run, cap inputs at `4Q`, and keep a target success gate. **Explicit fix**; a state-dependent re-normalizer can still be a formal potential if state is augmented, but changes the intended objective signal and finite residual. |
| **Use repeated zero-cost actions to collect positive shaping.** `get_elapsed_ticks()` reads a synthetic `storage.elapsed_ticks`; a no-op can leave it unchanged while the unpaused game and RCON calls proceed (`fle/env/instance.py:124-131`, `fle/env/gym_env/environment.py:433-449`, `fle/env/gym_env/environment.py:519-523`). | Use true `game.tick` deltas, enforce a step budget and a minimum transition duration/step cost where appropriate, and correct terminal `Φ`. For a genuinely zero-time closed loop, exact potential differences sum to zero, so **the theorem does suffice** under its assumptions; synthetic time and cutoff do not. |
| **Spike one good 60-second window, then starve the factory while claiming success or repeated high reward.** Existing `verify` keeps the maximum across increasing windows and returns it as reward; no sustained-rate test is present (`fle/eval/tasks/throughput_task.py:70-93`, `fle/env/gym_env/environment.py:469-474`). | Judge one prespecified final window after warm-up, optionally require two consecutive windows, and pay `R_success` once. **Explicit task/measurement fix**; shaping invariance says nothing about a misdefined base success signal. |
| **Create production-rate spikes by dumping items or resetting counters.** A short window turns one item into 60/min and `ProductionFlows.get_new_flows` discards negative deltas; reset clears production stats (`fle/commons/models/achievements.py:62-70`, `fle/env/tools/admin/reset/server.lua:21-32`). | Use episode-local counter baselines, detect counter resets and reinitialize EMA, and require 60-second automatic count for success. **Explicit estimator fix**; rate-history state must be part of the Markov state. |

Additional caution: `error_penalty` is currently subtracted **unconditionally**, while `error_occurred` is only a text search. The proposed `c_invalid·1[invalid]` needs a structured adapter outcome and must not confuse failed checks with operations that partially mutate the world (`fle/env/gym_env/environment.py:450-451`, `fle/env/gym_env/environment.py:469-474`, `fle/env/tools/agent/craft_item/server.lua:161-173`).

## 7. Time cost and episodes

`Δt` should be **actual simulated game ticks / 60**, with `τ` expressed in game seconds; reward then charges time when the factory, fuel, research and enemies progress. Wall-clock latency depends on Python/RCON/observation work and the registry sets game speed to 10, so wall time is a throughput engineering metric, not a fair in-world reward clock (`fle/env/gym_env/registry.py:138-145`, `fle/env/gym_env/registry.py:184-193`, `fle/env/gym_env/environment.py:307-334`, `fle/env/gym_env/environment.py:436-449`). Crucially, the exposed `get_elapsed_ticks()` is **synthetic** `storage.elapsed_ticks`; fast crafting and `sleep` add to it directly, while `sleep` merely returns `game.tick` in Lua and ignores it in Python. The Gym `game_info.tick` and `info["ticks"]` inherit the synthetic counter, so **they are not verified true simulation time** (`fle/env/instance.py:124-135`, `fle/env/tools/agent/craft_item/server.lua:161-168`, `fle/env/tools/agent/sleep/server.lua:1-9`, `fle/env/tools/agent/sleep/client.py:37-49`, `fle/env/gym_env/environment.py:322-326`, `fle/env/gym_env/environment.py:503-507`). A future adapter needs to read authoritative `game.tick` at transition boundaries and pause consistently; deterministic exact-tick stepping is **UNVERIFIED** in the current code. Do not silently use synthetic ticks in `γ^(Δt/τ)`.

The bounded task config advertises 64 steps and a 60-second holdout, but Gym itself never increments a task step counter or sets `truncated=True`; it only sets `terminated=success`. The Inspect solver enforces trajectory length with its own `for step in range(trajectory_length)` loop (`fle/eval/tasks/task_definitions/lab_play/throughput_tasks.py:40-47`, `fle/env/gym_env/environment.py:453-465`, `fle/env/gym_env/environment.py:519-523`, `fle/eval/inspect/integration/solver.py:332-348`). Unbounded throughput config advertises 16 steps; default/open play advertises 5000; those are config/runner budgets, not native Gym terminations (`fle/eval/tasks/task_definitions/unbounded/unbounded_tasks.py:35-48`, `fle/eval/tasks/task_definitions/unbounded/unbounded_tasks.py:66-72`, `fle/eval/tasks/task_definitions/unbounded/unbounded_tasks.py:96-101`, `fle/env/gym_env/environment.py:453-465`).

**V0 proposal:** cap each episode at **32 policy actions or 600 true game seconds**, whichever comes first; reserve a final 60-second automatic-production holdout after a fixed 30-second warm-up, and terminate early only after that holdout meets quota. At either budget limit, truncate and force terminal potential to zero (or subtract the residual); pay time cost for holdout time as well. These are design parameters, not existing behavior. Thirty-two actions gives the raw-ore task room for location, placement, fueling, recovery and a validation window, while being shorter than the existing 64-step LLM trajectory (`fle/eval/tasks/task_definitions/lab_play/throughput_tasks.py:40-47`, `fle/eval/tasks/task_definitions/lab_play/throughput_tasks.py:175-180`). It also limits the expensive current pattern of multi-window verification after every action (`fle/eval/tasks/throughput_task.py:70-93`, `fle/env/gym_env/environment.py:455-459`). At speed 10, 600 nominal game seconds corresponds to about 60 wall seconds **of simulation wait alone**; actual per-step wall latency, exact holdout tick count, and achievable PPO rollout rate are **UNVERIFIED** without a benchmark, which this research intentionally did not run (`fle/env/gym_env/registry.py:184-193`, `fle/env/tools/agent/sleep/client.py:43-51`). Revisit the budget only after measuring that latency and success traces.

## 8. Top five reward/task risks

1. **The proposed policy-invariance claim is too strong for the current episodic setup.** The finite boundary term survives, Gym has no horizon truncation, and the current quota max is an every-step reward (`fle/env/gym_env/environment.py:453-474`, `fle/env/gym_env/environment.py:519-523`). Specify matching discounts, rate-history state and terminal-potential correction before claiming invariance.
2. **Per-step verification changes and slows the world.** `verify` runs at least two 60-second nominal sleeps and possibly more, selecting a maximum window; `sleep` does not advance exactly 60 game seconds (`fle/eval/tasks/throughput_task.py:70-93`, `fle/env/tools/agent/sleep/server.lua:1-9`, `fle/env/tools/agent/sleep/client.py:37-51`). Move success measurement to a fixed final holdout.
3. **Offline recipes are insufficient for quantitative DAG weights or machine sizing.** They contain ingredients but no outputs, time, category or unlock effects; live serialization has most missing recipe fields, while its Python wrapper discards some (`data/recipes/recipes.lua:988-1004`, `data/recipes/main.py:23-26`, `fle/env/mods/serialize.lua:594-610`, `fle/env/tools/agent/get_prototype_recipe/client.py:35-53`). Keep V0 to an acyclic restricted chain and export prototypes before broader targets.
4. **Production rate and stock are not already reliable per-step state variables.** `ProductionFlows` has cumulative maps and deltas but no timestamps/EMA, manual work can enter raw counters, and Gym observes only player inventory plus entity snapshots rather than a deduplicated factory total (`fle/commons/models/achievements.py:14-39`, `fle/env/utils/achievements.py:18-40`, `fle/env/gym_env/environment.py:307-334`). Define an authoritative automatic counter and stock aggregation contract.
5. **The task difficulty implied by existing IDs is misleading for from-scratch PPO.** Even the easiest ore task provides 50 drills/500 coal and all research, while plate and circuit tasks add progressively more recipe branches at the same 16/min quota (`fle/eval/tasks/throughput_task.py:9-31`, `fle/eval/tasks/throughput_task.py:50-56`, `fle/eval/tasks/task_definitions/lab_play/throughput_tasks.py:81-86`, `fle/eval/tasks/task_definitions/lab_play/throughput_tasks.py:175-187`, `data/recipes/recipes.lua:989-1004`). Report stocked-training success separately from genuine bootstrap success and use the explicit 8-plate curriculum if from-scratch behavior is the target.
