# Simulator observation protocol improvements

This is a code-grounded implementation specification for extending PR #414 on `feat/pufferlib-rl`. The target is `fine_grid (12,32,32)`, `coarse_grid (6,32,32)`, `entity_view (512,32)`, `entity_mask (512,)`, player `inventory (128,2)`, `flows (128,4)`, a live-size `tech_mask`, and task and global vectors of about 16 values each. These shapes deliberately supersede the smaller V0 in `docs/rl/DESIGN.md:9-20,49-59`. No Factorio process, Docker container, benchmark, or test was run for this document. Runtime API details and performance below that cannot be established from this checkout are marked **UNVERIFIED**.

The existing response is one entity string, one `~`, and one terrain string. The entity string starts with `h<tick>:<research|->:<percent>:<player-x>:<player-y>`; records use `;` separators. Existing entity records are `u`, `r`, `q`, and `!`; terrain records are `c`, `o`, `d`, `t`, `k`, `x`, `n`, `m`, and `!` (`fle/cluster/scenarios/open_world/observation_diff.lua:23-39,391-428`). Keep those records and the first five header fields. Add versioned records to the entity side of **the same** `obs_all_drain()` reply. Full sync remains a cold-attach or recovery operation (`fle/cluster/scenarios/open_world/observation_diff.lua:430-473`).

## Gaps that require a protocol or client change

| Target signal | Current evidence and why it is insufficient | Required change |
|---|---|---|

| Physical electric state | A row has only `N<electric-network-id>`, an arbitrary identity; `TensorClient` exposes that ID as a float (`fle/cluster/scenarios/open_world/observation_diff.lua:129-134`; `tests/benchmarks/benchmark_tensor_obs.py:74-76,247-248`). Live statistic semantics are **UNVERIFIED**. |

| Representative 512 entities | The benchmark has a capacity-limited 2,048-row table and selects nearest first, using `argpartition` without a stable unit-number tie-break (`tests/benchmarks/benchmark_tensor_obs.py:77-83,218-227,437-468`). A distant failed furnace can disappear behind belts. | Keep an unbounded client dictionary and select 511 stratified real rows plus the player anchor. |

Task text itself stays outside Lua. |

## Wire contract and emission tiers

Use protocol version 2. Append `:<epoch>` to `h`, preserving the original five fields. `epoch` is a monotone scenario-session/reset generation. Emit `v2:<epoch>:<vocabulary-sha256>` once in each entity full sync and after an epoch change; require a matching checked-in artifact before encoding. The vocabulary hash is computed by the host from the startup export and made available to the Lua module through a generated manifest or a one-time initialization call. The exact mechanism for passing it into the scenario is an implementation detail, but an unvalidated hash must never be sent as proof. Implement one shared entity-tier serializer used by `obs_diff_drain()`, the entity half of `obs_all_drain()`, and `obs_diff_full_sync()`, so the new records cannot diverge across APIs. Emit records in this order: header, version/technology if due, inventory deltas, `u/r/q/a` changes, one coalesced `f@` batch, then one `g@` batch. Old clients ignore unknown record tags and extra header fields in their existing parsers (`tests/benchmarks/benchmark_tiered_obs.py:32-55`; `tests/benchmarks/benchmark_tensor_obs.py:301-314`). The new client rejects a missing/wrong `v2`, a changed epoch without fresh snapshots, malformed records, or any `!overflow`; it pauses, creates new dictionaries, and applies both full syncs. Since the two full-sync functions are separate calls, pause the world during recovery and verify equal header epochs/ticks before resuming (`fle/cluster/scenarios/open_world/observation_diff.lua:391-473`; `docs/rl/DESIGN.md:116-119`).

All new records below are semicolon-separated on the entity side of `~`. Names are checked against the startup vocabulary and must be delimiter-safe or escaped; the existing wire assumes unescaped prototype names (`fle/cluster/scenarios/open_world/observation_diff.lua:29-39,85-86,210-223`). A v2 parser must reject unknown names rather than silently assigning session IDs. Numeric output uses base-10 ASCII integers unless stated otherwise. `-` means unavailable only where specified. Exact values remain in wire records where the legacy protocol did so; normalized features are a client decision.

No per-tick full-table age payload. |

The `f` and `g` records are batches: the parser applies their header and following rows atomically, retaining previous rows not mentioned; `valid=0` means the associated rates or measurements must not be used as observed zero. For item rates, define production and consumption only after a live one-item producer/consumer calibration establishes which Factorio counter direction means which. The current production tool labels `input_counts` consumption while `score/server.lua` calls `input_counts` produced, so the direction is **UNVERIFIED** (`fle/env/tools/admin/get_production_stats/server.lua:14-39`; `fle/env/tools/agent/score/server.lua:1-11`). Compute a trailing rate as `window_count * 3600 / actual_window_ticks`, then round to tenths for the wire. Include a validity/age scalar in globals because a 600-tick sampling tier is intentionally not instantaneous.

Define `stored` explicitly as **surveyed item stock**: player main inventory plus inventories of tracked force-owned containers and machines on the observed surface, including input, output, and fuel inventories where the live prototype supports them. Add a `stock_row(e)` helper to `observation_diff.lua` that reads each validated inventory kind once, caches per-entity item contributions in `storage.obs_diff`, and subtracts the old contribution before adding a new one on every event/touch/reconciler check, even when the rich-row signature is unchanged. Removal subtracts the old contribution. The `f` row carries exact stock **at its last bucket-changing emission**; the client uses `stock-value-tick` to show any staleness. Do not call this exact force-wide inventory: belts, transit, untracked entities, and unsurveyed or stale inventories are outside that definition. Publish stock coverage and max stock-row age in globals; `stored` is invalid if its coverage is incomplete. The current entity loop only visits inventory indices 1 through 4, so it cannot be reused as proof that every machine/fuel inventory is covered (`fle/cluster/scenarios/open_world/observation_diff.lua:140-148,162-179,305-328`; `fle/env/tools/agent/inspect_inventory/server.lua:56-78`). To offer a truly exact force-wide stock later would require a separate, measured full scan or event coverage for all item carriers. Its runtime cost is **UNVERIFIED**. This explicit bounded metric is preferable to a falsely exact field.

For power, use one representative electric pole per `(surface, network-id)` and the live electric-network statistics API to measure generation and consumption over the same 60-tick interval, convert energy per interval to watts, and define `satisfaction = min(1, delivered/demand)` with demand zero giving 1. The repository proves only that a pole exposes `electric_network_statistics` and shows a commented `get_flow_count` sketch; the callable method, category direction, interval, and whether unmet demand is reported are **UNVERIFIED** (`fle/env/mods/serialize.lua:813-823`). A startup calibration must compare a generator with an idle and a loaded electric consumer, then an underpowered consumer, against observed `entity.status` and meter values. If unmet demand cannot be recovered from those counters, add a server-side per-consumer requested-versus-delivered measurement using a validated Factorio API and batch it by network; until that is validated send `valid=0`, not a fabricated satisfaction of 1. The client joins each row's existing `N` to the latest `g` but embeds `log1p(supply W)`, `log1p(demand W)`, and satisfaction or their missingness, never `N` itself (`fle/cluster/scenarios/open_world/observation_diff.lua:129-134`; `tests/benchmarks/benchmark_tensor_obs.py:247-248`).

**Cost model.** The existing `obs_all_drain()` already combines two tiers into one RCON response (`fle/cluster/scenarios/open_world/observation_diff.lua:413-428`). All proposed steady-step fields use that call, so added RCON round trips per step are **zero**. A startup vocabulary export, two full syncs, and a possible one-time focus setup remain cold operations. **Estimate:** an idle drain adds 0 record bytes beyond the appended epoch; a normal action changing two inventory kinds, one entity, and one stock row adds roughly 80 to 220 ASCII bytes; a scheduled flow batch adds roughly 0.6 to 1.1 KiB for 20 active kinds. These are payload estimates, not measured latency. Lua work adds an O(player inventory slots) drain-time scan, bounded counter/network samples, and the reconciler work below. Actual drain p50, response size, and UPS impact are **UNVERIFIED**; the audit's reported 1.7 to 39 ms observations concern older workloads, not this design (`docs/rl/research/02-observation-space.md:75-89`).

## Live status codebook and fault groups

At startup export `defines.entity_status` as sorted `{name,integer}` pairs alongside Factorio version, installed mods, entity/item/recipe/technology names and the canonical hash. Commit the generated artifact at the location already proposed by the design, `data/rl/vocab/factorio-2.0.73-base-v1.json`, and reject an environment whose live export hash differs. Do not derive codes with `EntityStatus.from_int`; its declaration-order implementation has no established relation to Factorio codes (`fle/env/entities.py:43-50,155-167`; `docs/rl/DESIGN.md:49-53`). Generate a `status_code -> group_index` table **from the exported live names**. Check that each name is assigned at most once. Suggested indices are `0=other`, `1=working`, `2=no_power`, `3=no_fuel`, `4=starved`, `5=output_blocked`, `6=disabled`.

Grouping is exact-name based after the live export, not a guess about integer order. `working` maps to working; `no_power`, `low_power`, `not_plugged_in_electric_network`, and `recharging_after_power_outage` map to no_power; `no_fuel`, `no_food`, and `low_temperature` map to no_fuel; `no_ingredients`, `item_ingredient_shortage`, `no_input_fluid`, `low_input_fluid`, `fluid_ingredient_shortage`, `missing_required_fluid`, `missing_science_packs`, and `waiting_for_source_items` map to starved; `full_output`, `full_burnt_result_output`, `not_enough_space_in_output`, and `waiting_for_space_in_destination` map to output_blocked; `disabled`, `disabled_by_control_behavior`, `disabled_by_script`, `paused`, `frozen`, and `broken` map to disabled. These names exist in the Python enum, **not yet in a verified live code map** (`fle/env/entities.py:46-64,73-103,128-150`). A live name absent from a list, a raw code absent from the export, `normal`, `none`, `empty`, and any ambiguous status map to `other`; count unknown codes as a diagnostic and fail startup on a vocabulary hash mismatch. `no_recipe`, `no_research_in_progress`, and `no_minable_resources` remain `other` unless a task explicitly establishes that they are faults, because a missing recipe or exhausted patch can be intentional (`fle/env/entities.py:73-97`). Do not label every neutral entity working.

The coarse starved fraction is deliberately the combined **input/fuel-starved** group: `(group 3 + group 4)/eligible_count`. The four requested coarse fault channels are working, no_power, input/fuel-starved, and output_blocked. Keep group 3 distinct in entity rows. An eligible entity is a tracked player-force functional machine or logistics entity with a live status code; exclude character, ghosts, and decor. Include disabled and other eligible rows in the denominator so four fractions need not sum to one. An empty cell has four zeros plus density zero, while its known fraction distinguishes known empty from unexplored. Group and eligibility rules must be pinned to the live artifact and task classifier, not inferred from the raw integer. The current grid has no denominator and only a status sum (`tests/benchmarks/benchmark_tensor_obs.py:198-214`).

## Terrain tier and persistent egocentric map

The ore-producing Lua today is:

```lua
local ores = surface.find_entities_filtered{ area = area, type = "resource" }
if #ores > 0 then
  local cache = {}
  for i = 1, #ores do
    local o = ores[i]
    local key = pos_key(o.position)
    local bucket = math.floor(o.amount / RES_BUCKET)
    cache[key] = bucket
    emit("o" .. o.name .. ":" .. key .. ":" .. bucket)
  end
  s.res_chunks[#s.res_chunks + 1] = { area = area, cache = cache }
end
```

This is from `fle/cluster/scenarios/open_world/observation_diff.lua:212-224`; `RES_BUCKET=100` is at line 43. Change only the cache value to `{name=o.name,bucket=bucket}` and compare both fields in the later scan at `fle/cluster/scenarios/open_world/observation_diff.lua:330-343`. Keep `o<name>:<x>:<y>:<bucket>` unchanged so existing clients still parse it. If multiple resource entities can occupy one tile, the current `key=pos_key` silently overwrites one; that possibility is **UNVERIFIED**. The v2 implementation should either reject such overlap in the startup/live fixture or use one record per `(name,tile)` and a name-qualified depletion key. The latter is a protocol-version change and must be tested before claiming lossless resource layers.

On the client, a `c` record marks all 1,024 tiles in that chunk **known**, even when its water hex string is empty. Keep sparse or chunked arrays for `known`, `water`, `obstacle`, `resource_type_id`, and `resource_bucket`; preserve trees and rock/cliff points as obstacle contributors. An `o` writes type and bucket at its tile, replacing any old type; `d` clears it. `x` clears tree/rock/cliff state. `c` and initial/full-sync chunk iteration populate the map; new generated chunks stream through `on_chunk_generated` (`fle/cluster/scenarios/open_world/observation_diff.lua:187-238,244-248,277-282,455-473`). A full sync replaces the map, not just its values. The benchmark's `water` dictionary already shows how chunk presence can mark known terrain, but the current tensorizer drops resource type (`tests/benchmarks/benchmark_tiered_obs.py:17-23,57-70`; `tests/benchmarks/benchmark_tensor_obs.py:361-380`).

Use player `floor(x),floor(y)` as the fine center and fixed half-open world windows. Fine cell `(i,j)` reads tile `(floor(px)-16+i, floor(py)-16+j)`. Define its 12 channels as: known; `iron-ore`, `copper-ore`, `coal`, `stone`, and `uranium-ore` resource occupancy/amount; water; obstacle; mining; crafting/smelting; transport/inserter; and storage/power/other functional structure. The five ore channels retain type identity; encode each **present** ore as `0.1 + 0.9*min(1, log1p(100*bucket)/log1p(10000))`. The 0.1 floor distinguishes a present resource with a zero amount bucket from no resource. Other resource names remain in the persistent map and are diagnosed as unmapped; never merge them into these five channels. Put the fixed 10,000-unit saturation scale and name-to-channel mapping in the versioned client schema. If quantity fidelity is not needed for a task, occupancy can be a derived binary view, not the stored representation. Classify structures from checked-in entity prototype type/name mappings and rasterize their exported footprints, clipping each fine functional channel to 1 (`fle/cluster/scenarios/open_world/observation_diff.lua:109-115,212-223`; `docs/rl/DESIGN.md:49-57`). Prototype footprint alignment and overlap with tiles must be tested on the live version; exact center parity is **UNVERIFIED** (`docs/rl/DESIGN.md:49-53`).

Coarse cell `(i,j)` covers the 4×4 tile block starting at `(4*floor(px/4)-64+4*i, 4*floor(py/4)-64+4*j)`, for 128×128 total coverage. Its six channels are known-tile fraction; eligible functional-entity density `min(count/16,1)`; working fraction; no-power fraction; input/fuel-starved fraction; and output-blocked fraction. Derive density and status from entity positions/footprints, counting **each entity once** by center cell, not once per footprint tile. Ore and water remain available as 4×4 pooled slices of the persistent typed tile map to the encoder or a later wider coarse schema; with only six target coarse channels, the four required fault fractions and a known/density pair fill all slots. The fine map carries typed ore locally; a task needing typed ore at 128-tile range should revise the six-channel contract explicitly rather than silently fold five ores into one coarse lane. Unknown fine content is zero with known=0; an all-unknown coarse block has known fraction 0 and all other channels 0. A partly known coarse block reports its known fraction and computes terrain fractions over known tiles only, never interpreting missing records as dry/ore-free land. Entity status fractions use eligible known-placed entities as denominator and carry separate freshness diagnostics. This is a design choice, not an existing behavior (`docs/rl/research/02-observation-space.md:66-72`; `tests/benchmarks/benchmark_tensor_obs.py:44-58,198-214`).

**Memory estimate:** a 1,024×1,024-tile explored square is 1,048,576 tiles. One byte of resource type plus a `uint16` bucket is 3 MiB; three bitsets for known, water, and obstacle add 0.375 MiB. Allow roughly **3.4 to 5 MiB** including chunk indexes and alignment, excluding the separate entity dictionary and Python object overhead. Five dense `uint16` ore planes would cost 10 MiB before masks, so the type-plus-bucket representation is preferable. Actual explored area and ore bucket bounds are **UNVERIFIED**. If buckets can exceed 65,535, use `uint32` or saturate only the policy feature while keeping the exact integer in a sparse overflow map.

## Bounded, prioritized reconciliation and row freshness

Replace the single 50-per-47-tick cursor with four persistent queues indexed by 32×32 spatial buckets and unit number. Keep entity references and bucket membership updated on build, removal, movement detected by checks, and full sync. Each 11-tick pass checks at most **56** entities: 24 round-robin from the 512 highest-priority entities within 64 tiles of the player, 16 from the 256 highest-priority entities in a task-focus circle of radius 64, 8 known problem/high-value machines ordered by oldest check, and 8 from the global round-robin. Entities beyond those local caps remain in the global queue and are marked stale when needed. De-duplicate within the pass and refill unused slots from the oldest eligible priority queue. Class priority within player/task queues is production and power machines, then inserters/logistics, then passive belts/chests; old checks win within class, then unit number breaks ties. Include a separate bounded nearby discovery query every 47 ticks and retain the current full-force discovery safety sweep every 1,504 ticks until live event coverage proves it unnecessary (`fle/cluster/scenarios/open_world/observation_diff.lua:41-46,250-286,290-328`). Use `obs_all_drain(focus_x,focus_y,focus_radius)` optional arguments to update the task focus in the same existing poll call; the last focus persists for intervening ticks. Initial focus can be set at reset, one cold setup call, or in the first drain. This avoids a per-step focus RCON call. The client may request a bounded synchronous `obs_all_drain` priority top-up for these selected stale units within the same call, but must never present stale data as current. `A` and `a` provide the required evidence; computing `game.tick-last_emitted_tick` alone would conflate an unchanged, repeatedly checked machine with an unchecked one.

**UPS cost estimate:** old entity re-row budget is `50/47 = 1.06` rich rows per game tick, ignoring discovery/resource work. The new budget is `56/11 = 5.09` rows per game tick, about 4.8 times that specific Lua work, plus `a` serialization. If one `rich_row` costs `c` microseconds, its incremental CPU demand is approximately `4.03*c` microseconds per game tick, or `4.03*c*UPS/1e6` CPU seconds per wall second. For `c=10 microseconds` and 600 UPS this is **estimated** 2.4% of one core; at `c=50 microseconds` it is **estimated** 12.1%. `c`, sustained UPS, spatial-index overhead, and the cost of `get_inventory` are **UNVERIFIED**, so a real implementation must measure them. For a 512-entity local pool, 24 checks per 11 ticks yield `ceil(512/24)*11 = 242` game ticks for one cycle, **estimate** 0.40 s at 600 UPS or 1.91 s at 127 UPS. A 256-entity task pool at 16/pass takes 176 ticks. A 20,000-entity global-only tail at 8/pass still takes 27,500 ticks, **estimate** 45.8 s at 600 UPS or 216.5 s at 127 UPS; those rows are explicitly aged and cannot be used as fresh policy inputs. This scheme bounds local correctness while showing, rather than hiding, remote uncertainty. If the live UPS budget fails, tune quotas/interval against measured p95 freshness and step throughput, not an assumed fixed 47-tick guarantee (`fle/cluster/scenarios/open_world/observation_diff.lua:290-352`; `docs/rl/research/02-observation-space.md:75-89`).

## Client-side stratified top K

Select on the **client** after each drain. The server must retain the full diff state and already pays to transmit changes; dropping unselected rows server-side would make future action targets, changed-area selection, and recovery ambiguous. The client has task metadata and the full entity dictionary, while the Lua module need only prioritize reconciliation around a supplied focus (`tests/benchmarks/benchmark_tiered_obs.py:14-30`; `tests/benchmarks/benchmark_tensor_obs.py:437-468`; `docs/rl/DESIGN.md:55-57`). Remove the benchmark's 2,048-row table cap for the production client. Keep a dictionary keyed by integer unit number and build a 512-row view from it; row 0 is the player anchor, 511 rows are real entities. Preserve a row-to-unit map for the entire action, since row order may change at the next observation (`tests/benchmarks/benchmark_tensor_obs.py:81-113,218-227,437-468`).

Fill five quotas in order, skipping already selected units: **191** nearest to the current player/task focus (distance to nearer focus), **128** task-relevant type/recipe/area candidates, **96** non-working or problem-status candidates, **48** spatially dispersed candidates, and **48** recently changed candidates. Fill unused quota from remaining candidates ranked by task relevance, freshness, then distance. Task relevance is an explicit task-schema predicate over entity type, recipe, goal item, footprint on goal resource, or inclusion in the task area; status alone does not make an unrelated decoration relevant. A problem candidate has a validated codebook group of no_power, no_fuel, starved, output_blocked, or disabled. For dispersion, partition the 128×128 coarse view into 4×4 regions, take the nearest eligible candidate per region before a second pass, and then expand outward by spatial bucket. Recent means latest `u`/`r`-related update tick among still-live entities; removal itself cannot occupy a row. Rank each quota by its stated primary metric, then `(squared distance, unit_number)`; ties in changed time use smaller unit number. This removes the current `argpartition` tie ambiguity (`tests/benchmarks/benchmark_tensor_obs.py:451-459`).

Report `selected_relevant_fraction = selected_relevant_count / total_relevant_live_count`, with 1 when there are no relevant live candidates, plus both counts and the number of stale selected rows. This is recall, so it can be below 1 when more than 511 entities are relevant. Example: 700 belts cluster around the player and one output-blocked furnace is 70 tiles away near the task ore. Nearest-first K=512 selects only belts (`tests/benchmarks/benchmark_tensor_obs.py:437-468`). The 96 problem quota selects the furnace, the task quota retains the task line, and the diagnostic reveals any relevant entities still omitted. If the furnace's status has not been reconciled yet, the age bit marks the row uncertain and the server's task/fault queues or bounded drain top-up must refresh it before the policy relies on that fault classification (`fle/cluster/scenarios/open_world/observation_diff.lua:290-325`).

Freeze the 32 entity lanes in client schema v2 as follows. IDs/group indices are integer-valued lanes consumed by embeddings; all other non-binary lanes are normalized and clipped as specified. A missing network measurement is zero with its network-validity lane zero. For a property not applicable to an entity type, zero is the documented value and the type embedding distinguishes it from an applicable zero (`tests/benchmarks/benchmark_tensor_obs.py:63-83,190-196,228-260`; `docs/rl/DESIGN.md:49-53`).

| 12 to 19 | `log1p(joules)/log1p(10000000)`; `log1p(fuel item count)/log1p(500)`; `log1p(all surveyed entity item count)/log1p(500)`; `log1p(fluid amount)/log1p(1000)`; pickup dx/dy and drop dx/dy, each divided by 8 and clipped to `[-1,1]`. Clip all log ratios to 1. |
| 20 to 23 | Joined `log1p(supply W)/log1p(1000000)`, `log1p(demand W)/log1p(1000000)`, satisfaction in `[0,1]`, and one network-measurement validity bit. Clip power log ratios to 1. |
| 24 to 31 | Value age/3,600 ticks capped at 1; check age/600 ticks capped at 1; fresh bit under the applicable age threshold; task-relevant bit; problem-status bit; recently-changed-within-600-ticks bit; overlaps-task-resource bit; entity-inventory-coverage bit. |

## What belongs in PR #414

The resource cache's name-plus-bucket comparison, same-call drain batching, unchanged-check freshness acknowledgements, overflow recovery contract, live status-code export, player-inventory drain, full technology snapshot, and a bounded priority reconciler are general observation-protocol improvements.
