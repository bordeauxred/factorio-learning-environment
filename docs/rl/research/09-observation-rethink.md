# Rethinking the RL observation after the live ladder

This is a design review of PR #414 and the RL observation built on it. It uses the one-map, one-training-seed ladder on map 44340, the recorded timing and reset measurements, and the checked-in encoder. No new simulator or training measurement was made here. The conclusion is to **keep the tiered wire protocol, replace the oversized RL representation, and keep observation layout fixed across curriculum stages**. The next experiment should use a smaller structured observation with a 64-row entity cap, a one-tile local placement map, a coarser typed navigation map, and compact replay storage. The most valuable single low-effort change is reducing the entity cap from 512 to 64 before another learner run.

## What the measurements establish

The live vector is 38,495 float32 values, or **153,980 bytes per boundary** (154 decimal KB, 150.4 KiB). The largest blocks are the 512 by 32 entity table (16,384 values), the 12 by 32 by 32 fine grid (12,288), and the 6 by 32 by 32 coarse grid (6,144). These three blocks occupy **90.4%** of the vector. The entity count in the successful ladder setups was only one to three, so almost every entity row was padding; most grid cells were also zero. The layout is defined at `fle/rl/schema.py:33-40,207-235`; the exact 38,495 width is independently recorded at `docs/rl/results/replay_optimization.md:9-15`.

The protocol is not the current per-step bottleneck. In the 128-step live sample, p50 whole step was 86.039 ms, tool dispatch 75.899 ms, drain 2.099 ms, encoding 3.110 ms, and masks 0.746 ms (`docs/rl/results/rung1.md:54-85`). These are *medians of different phases*, so they should not be subtracted to infer an exact residual. The recorded policy was 2.49 million parameters; batch-256 forward took 23.6 ms on MPS and an update took 69 ms, as reported with this review request. Those two model timings were not remeasured here. At the tested action mix the learner became the throughput constraint, and spending compute on roughly 508 to 510 absent rows has no information benefit. Behavior at a larger factory is **UNVERIFIED**; the old protocol audit reported much higher observation poll times and falling UPS at thousands of entities (`docs/rl/research/02-observation-space.md:77-89`).

The large reset bill was a separate cold-path error: warm legacy resets averaged 24.780 s, with the terrain full-sync RCON call taking about 24.8 s while FLE's own reset took about 0.17 s. Reusing the terrain cache brought warm reset to 0.126 s and matched one-container throughput from 1.880 to 6.975 steps/s (`docs/rl/results/reset_optimization.md:5-22,24-30,40-51`). The retained map is depleted across episodes, so that optimization changes the episode distribution; it is not a free fresh-map reset (`docs/rl/results/reset_optimization.md:28-30`). The 1.63 MB full terrain response and 24-second server work are not evidence that a normal diff drain is slow.

The learning results constrain the diagnosis. L0 reached 32/32 fresh greedy successes, L1 32/32, and L2 from scratch 0/24; 96 real demonstration transitions made L2 reach 32/32 on the same map and seed (`docs/rl/results/ladder.md:13-38,69-89,117-131,194-215`). L0's trained first action was MOVE, which also advances time; it did not prove the agent needed a detailed world map. L2's failed run had no assigned-goal success, one 2-ore episode, and 813 preflight-invalid actions in 2,029 non-WAIT training decisions. Its final policy repeatedly chose invalid tuples (`docs/rl/results/ladder.md:142-180,240-259`). A smaller observation is a plausible efficiency and generalization improvement, **not an established cure for L2 exploration or action factorization**.

## PR #414 as a foundation

**The architectural choice was right.** A persistent client cache fed by separate entity and terrain change streams gives one combined steady-step RCON response. The terrain tier sends named ore tiles, water chunk masks and static obstacles; the entity tier sends unit-keyed rich rows plus removals; hot fields emit on quantized changes (`fle/cluster/scenarios/open_world/observation_diff.lua:1-43,90-190,198-249,547-561`). It can serve several downstream encoders without forcing a new per-step server scan. The observed 2.1 ms drain vindicates that design for the small live worlds tested. Unit-number identity, explicit removal, chunk streaming and a full-sync recovery path are sound primitives. The wire is an observation **source**, not a reason to preserve the benchmark's tensor size.

For the general protocol, retain and finish the following upstream work:

1. **Correct state and recovery semantics.** The name-plus-bucket ore cache fix is necessary: a resource name can change while its amount bucket does not (`fle/cluster/scenarios/open_world/observation_diff.lua:223-235,367-387`). Preserve atomic full replacement on overflow, epoch and version checks, and a vocabulary hash so a replay/checkpoint cannot silently interpret new IDs. The current Lua emits a bare `v2`, while the client accepts it by setting `version=2`; the requested epoch/hash wire contract in `docs/rl/DESIGN.md:133-145` is not implemented by those records (`fle/cluster/scenarios/open_world/observation_diff.lua:451-452`; `fle/rl/observation.py:145-170`). The legacy entity-only drain and full sync still use different serialization paths from the combined v2 drain (`fle/cluster/scenarios/open_world/observation_diff.lua:525-561,596-619`); define which API is authoritative or share one serializer. Reuse of terrain on reset also needs an explicit map-generation/resource-regeneration contract, not an implicit assumption.
2. **Expose general facts in the existing drain.** Player main inventory, full researched/enabled technology state at attach/reset, true game tick, and exact production counter updates at action boundaries were the right additions. They remove extra queries and let the RL client compute action legality and HER labels. Per-ore-type *policy channels* were also the right choice for placement, though the wire already preserved ore names and did not require five dense planes (`fle/cluster/scenarios/open_world/observation_diff.lua:223-235`; `fle/rl/observation.py:383-406`). The reported entity-name cache bug fix is correctness work, not an RL feature: the current entity signature includes `e.name`, and the resource cache includes name and bucket, so an identity change can emit an update (`fle/cluster/scenarios/open_world/observation_diff.lua:95-98,172-181,223-235,367-387`). This source review does not independently measure the old bug's runtime impact. Row checks and value age were also right: a quantized signature can leave a cached count old even when the entity was recently checked (`fle/cluster/scenarios/open_world/observation_diff.lua:90-107,150-156,327-338`; `fle/rl/observation.py:172-184,502-510`). Keep raw network ID only as an internal join key, never as a numeric policy feature. Keep a live status-name codebook rather than assuming Python enum order (`docs/rl/research/06-simulator-improvements.md:47-53`).
3. **Close the remaining correctness gaps before claiming complete v2.** The implemented `automatic_counters()` subtracts manual output from `stats.input_counts`, clamps at zero, and the per-episode tier sends the already-derived `a` count. That is weaker than the design's proposed separate raw and manual counters with decrease rejection; counter direction and manual-ledger completeness remain **UNVERIFIED** without live calibration (`fle/cluster/scenarios/open_world/observation_diff.lua:432-472`; `docs/rl/DESIGN.md:53,83-89,135-137`). The tech snapshot is emitted as per-name bits on a slow audit; the client silently ignores indices beyond its 256-bit tensor (`fle/cluster/scenarios/open_world/observation_diff.lua:473-494`; `fle/rl/observation.py:530-534`). The Lua full sync is still an expensive whole-map enumeration when terrain is requested (`fle/cluster/scenarios/open_world/observation_diff.lua:564-594`). Define chunk paging or budgeted cold sync if new-map starts become frequent. The current priority reconciler is bounded but still scans all tracked entities to find the nearby 25 each pass, and only the checked age, not the raw-value age, is refreshed (`fle/cluster/scenarios/open_world/observation_diff.lua:304-365`). Its large-factory UPS and freshness guarantees are **UNVERIFIED**. Check the selected player identity: a missing character currently produces position `(0,0)` and an empty inventory, which looks like a valid state (`fle/cluster/scenarios/open_world/observation_diff.lua:393-429`).

The 12/6 grid channels, 512-row quota, 32-feature row, 128-row inventory/flow tables, action-mask shape and curriculum relevance heuristic belong in `fle/rl/`, not in PR #414's generic wire. This separation was correctly proposed in `docs/rl/research/06-simulator-improvements.md:136-140`. Lab-scenario loading remains **UNVERIFIED**; the open-world control loads this Lua, while the audited lab control did not establish it (`docs/rl/research/02-observation-space.md:91-95`). Do not make uncalibrated network watts or force-wide stock an upstream promise. The current wire sends `V0`, the flow table's stock lane is zero, and several planned globals and entity lanes remain zero (`fle/cluster/scenarios/open_world/observation_diff.lua:495-499`; `fle/rl/observation.py:491-510,518-549`).

## Derive the observation from the decisions

An observation should make the next **action** distinguishable, preserve enough state for credit assignment, and expose whether its facts are stale or unknown. The agent needs an exact goal and achieved vector for HER; episode time and remaining budget; player inventory and research/recipes for feasible work; a local one-tile map for harvest and exact placement; nearby entities with type, pose, status and relevant contents; and a coarser memory of resource patches, obstacles, factory faults and explored frontiers for navigation. Placement needs the ore tile, full footprint clearance, output direction and intended receiver. Multi-stage production needs item and machine identity, recipe, logistics and power dependencies, not a full float32 row for every belt on every step. The pinned static vocabulary can carry prototype footprints and recipes without repeating them in every observation (`docs/rl/DESIGN.md:47-65,67-79`).

**Entity set.** A fixed 512-row *policy tensor* is unjustified by one to three entities. It is also not a scale solution: once there are more than 511 real entities, selection still drops some. The current selection spends quotas of 191 nearest, 128 relevant, 96 faults, 48 dispersed and 48 changed (`fle/rl/observation.py:270-344`). That is a sensible overflow policy but untested at factory scale. Start with **64 rows including player anchor**, retain the complete unit-keyed client cache, select 63 diverse/actionable entities, and log total count, task and fault recall, age, and whether a successful action target was omitted. Keep row-to-unit mapping with the boundary and selected action. Later allow a variable set or bucketed batches capped by measured compute and recall. The existing shared row MLP plus masked mean/max and pointer scores already has set-like semantics but pays for all 512 rows (`fle/rl/policy.py:134-153,173-188`). Attention or graph message passing may help when the decisive fact is a relation such as drill-to-chest output, inserter pickup/drop, or connected power; it costs roughly quadratic attention work or explicit edge construction. First give a compact candidate/edge feature for those relations and compare against the current set encoder. A variable set does not remove the need to cap action candidates or preserve replay-time row identities.

**Spatial scales.** Keep a **32 by 32 one-tile fine view** for the next placement experiment. The offset head covers `[-8,8]` in both axes, so 17 by 17 is the minimum center window; footprints, reach and an output receiver need a margin. The current 32-tile width supplies roughly eight extra tiles on each side. Do not coarsen this placement view to four-tile cells: two centers with different ore coverage or collision can map to one cell (`fle/rl/schema.py:103-108,166-185`; `fle/rl/observation.py:378-406`). Exact candidate-center geometry should ultimately come from this one-tile map or a small affordance list. Use the second grid for navigation, not for placement. A **16 by 16 grid at eight tiles per cell** keeps the current 128 by 128 extent at one quarter the cell count. Give it 12 channels: known, water, obstacle, five typed ore occupancy/grade summaries, entity density, no-power, input/fuel-starved and output-blocked. Typed remote ore is more useful for deciding where to walk than a four-bin status decomposition that cannot say whether a distant patch is iron or copper. At eight-tile resolution, exact placement is deliberately delegated to the fine map. Beyond 64 tiles, a fixed egocentric crop still forgets useful discoveries; add a sparse list of remembered resource patches and exploration frontiers with type, relative direction/distance, extent and age before enlarging a dense grid. The current coarse grid has no ore identity at all (`fle/rl/schema.py:60-70`; `fle/rl/observation.py:407-463`).

The present `known` bit means **generated chunk delivered by the protocol**, not necessarily terrain the agent visited or saw (`fle/cluster/scenarios/open_world/observation_diff.lua:198-249`; `fle/rl/observation.py:390-401`). That is an information rule for the open track: decide explicitly whether generated but unvisited terrain is visible. If exploration is intended, maintain a visited/revealed mask separately and restrict patch/frontier summaries to permitted information. The current one-tile fine grid classifies a structure by name substring and marks only its center, despite the earlier design calling for footprint rasterization (`fle/rl/observation.py:420-438`; `docs/rl/research/06-simulator-improvements.md:76-80`). This can hide actual placement collisions. Correct footprint/occupancy semantics matter more than increasing spatial width.

**Interface.** The flat `Box` was expedient when a general trainer API was expected. PufferLib is no longer in the architecture (`docs/rl/research/07-rl-stack.md:8-23`; `fle/rl/env.py:124-134`). The network already slices the flat vector into separate grid, entity, inventory, flow, technology and goal encoders (`fle/rl/policy.py:118-172`). A named, typed observation would make that actual structure explicit: byte/bit grids, integer IDs, float16 or float32 continuous policy fields, exact float32 achieved/goal/tick, and action candidates or masks as a separate legality object. It allows sparse/ragged entities and avoids converting bits and IDs to float32 only to cast them back. Costs are a more complex batch collator, replay serializer, fingerprint and checkpoint migration, and potentially less convenient Gym interoperability. A dict alone saves **zero bytes** if all values stay dense float32; the benefit comes from changed shapes, types and sparse batching. Keep a named schema with strict versioning, and allow a temporary flat adapter for comparisons.

**Two different minimums.** On the fixed L0 setup, a policy can succeed from a task phase/time signal and legal actions, since the fuelled drill already produces ore while actions advance time. L1 additionally needs to know that coal is held and which drill lacks fuel. L2 needs the drill item, coal, ore tiles at one-tile resolution, a receiver and direction/footprint geometry, plus exact progress and legal actions. A task-specific 17 by 17 map with a few binary/byte channels, three compact entity records, inventory bits/counts, goal/tick and packed masks would be on the order of **0.5 to 2 KB per boundary**; this is an engineering estimate, not an information-theoretic minimum or a measured ablation. A memorized three-action script could use even less on map 44340, but would say nothing about transfer to another patch or layout. For the full open track, a plausible *starting budget* is **roughly 20 to 30 KB stored per boundary**, with a one-tile local crop, typed regional map, tens of selected entities, sparse inventory/flows, exact goals/counters, and patch/frontier memory. This range is an estimate, not evidence that 64 rows suffice in a large factory. The key gap is between kilobytes for a local drill sequence and tens of kilobytes for exploration and multi-stage production, rather than between 154 KB and an unbounded world dump.

## Replay arithmetic and options

The current buffer stores one full observation per **real** transition, one final boundary per episode, and HER goal overlays by reference; it does not store independent `s` and `s'` for every transition (`fle/rl/replay.py:82-96,117-120,353-397`; `docs/rl/results/replay_optimization.md:47-56`). For 64-action episodes, finals add about 1.56%. The arithmetic below excludes metadata, batch buffers, checkpoints and MPS memory. Decimal GB is used consistently.

| In-memory boundary format | Bytes per boundary | 200,000 real rows | Meaning |
|---|---:|---:|---|
| Current 38,495 float32 | 153,980 | 30.80 GB | About 31.28 GB with 64-action finals; cannot safely fit the observed host headroom. |
| Same shape, float16 for all 38,286 policy-only lanes, 209 exact float32 lanes | 77,408 | 15.48 GB | A ceiling on a simple half-precision scheme; some categorical IDs need integer storage to remain exact. |
| Same shape, grids as uint8, entity/inventory/flow continuous lanes as float16 with integer IDs, binary masks/tech/entity occupancy bit-packed, exact lanes float32 | about 53,938 | about 10.79 GB | Illustrative mixed-type packing; byte grids require a defined quantizer and error check. |
| 64 entities, otherwise current float32 shapes and action heads | 91,260 | 18.25 GB | Removes 15,680 floats per boundary, including two 448-wide pointer-mask reductions. |
| Proposed 64-entity, 32 by 32 fine and 16 by 16 coarse structured shape, all float32 | 78,972 | 15.79 GB | Separates the representation change from compression. |
| Same proposed shape with byte grids, half-precision continuous rows/tables, bit-packed masks and tech, exact lanes float32 | about 22,026 | about 4.41 GB | Target budget before small landmark/affordance sidecars and finals. |

The **209 exact lanes** are 104 achieved counts, 104 goal counts and one episode tick in this pinned vocabulary. They take 836 bytes and must remain lossless because HER compares thresholds and duration discounts use true tick (`fle/rl/schema.py:8-14,220-235`; `fle/rl/observation.py:535-543`; `docs/rl/DESIGN.md:51-53,83-89`). The current 30,000-row practical cap is a headroom projection, not a measured saturation point: 30,000 raw rows take 4.62 GB, while the profiling run saw only 6.71 to 9.16 GB free and reserved space for training/transients (`docs/rl/results/replay_optimization.md:72-101`). A byte grid is valid only after quantization tests on ore grade and known fractions; float16 is acceptable for bounded *policy* values if it does not alter critical placement/action decisions. Store IDs as integers large enough for the pinned catalog, and never coerce exact counts through float16. The mixed-type numbers assume 64-episode finals are added separately and do not promise total RSS.

Re-encoding compact state on sample can beat stored tensors if the state record contains only the local tile patch, selected unit records, sparse inventories and exact counters. It needs a deterministic encoder, versioned raw-state snapshots, replay-time row/goal/legality context and a low-cost path for n-step and HER; reconstructing each boundary from an ever-growing map diff chain would make random replay reads expensive and fragile. The prior replay implementation repeatedly decompressed full observations and took 665 to 904 ms per batch, compared with about 45 ms after moving to contiguous float32 gathers (`docs/rl/results/replay_optimization.md:27-45,47-56`). That result argues for **compact, directly indexable boundary records with vectorized decode**, not for zlib-on-every-sample. A memory-mapped float32 array shifts 30.80 GB from RAM to disk but does not reduce bytes read: a batch-256 current/next pair is about **78.84 MB** before transfer, roughly 1.14 GB/s if sustained at one 69 ms update. Random access and page faults may become the bottleneck; mmap is a fallback when capacity exceeds RAM, not the first representation fix. The mixed 22 KB target cuts that pair's stored read volume to about 11.3 MB before decoding, an estimate that must be profiled.

## Signal quality and curriculum

Stable integer ID lanes with embeddings earn their place for entity, item, recipe and status identity; action IDs must stay pinned across runs (`fle/rl/schema.py:42-84,261-278`; `fle/rl/policy.py:82-100,134-142`). But the current encoder reserves four categorical lanes and uses name-substring functional classes; several names can collapse into an unhelpful class. Use the live prototype type/category map to encode capabilities. `log1p` for nonnegative magnitude and fractions for progress or fault prevalence are reasonable policy transforms, provided saturation and validity are explicit. The current flow fourth column is always zero, power lanes 20 to 23 and entity lanes 30 to 31 are never filled, and many globals are zero; carrying them in replay and the learner is wasted until they have defined semantics (`fle/rl/observation.py:491-510,518-549`). More seriously, `stored=0` or power-valid=0 must be read as missing, not as zero physical stock or no demand. Per-cell status fractions are useful once eligibility excludes character/decor, row ages are bounded, and a valid codebook exists. The current coarse aggregation counts **every** cached entity in its density denominator, which can dilute a machine fault (`fle/rl/observation.py:420-462`; `docs/rl/research/06-simulator-improvements.md:47-53`).

Player-relative positions make nearby placement generalizable, but current row coordinates clip at 64 tiles, so distant entities can become directionally indistinguishable; a patch/landmark list should carry coarse direction and distance separately (`fle/rl/observation.py:484-500`). Direction sine/cosine, recipe, status, fuel and output geometry can distinguish the L2 chest-feed failure. Dropping raw electric-network ID from policy features was correct: network identity is arbitrary, while power availability and connection are physical. It remains **UNVERIFIED** how to derive demand/satisfaction from the live API, and the present `V0` is the honest value (`fle/cluster/scenarios/open_world/observation_diff.lua:495-499`; `docs/rl/research/06-simulator-improvements.md:41-43`). Value age and check age should both remain: a fresh comparison of quantized values is not an exact fresh item count. Freshness belongs in action admission as well as the critic, especially for insert/extract and routing (`fle/rl/observation.py:502-510`; `docs/rl/research/06-simulator-improvements.md:84-90`). The open track still needs an explicit explored/visited distinction, remote typed resource memory, receiver/port and machine-item affordances, inventory capacity/slot support, and local connectivity information. These are missing *relations*, not an argument for more padded entity rows (`docs/rl/research/08-action-space-rethink.md:23-27,46-54`).

Do **not** change observation shape with each curriculum stage. The replay store uses a single `schema.size`, the fingerprint rejects other layouts on load, and the policy's first layers and pointer widths are built from that shape (`fle/rl/replay.py:69-96,459-464`; `fle/rl/schema.py:207-278`; `fle/rl/policy.py:75-115`). A shape change invalidates old transitions for the new encoder, prevents direct mixed-stage batches, and requires checkpoint weight surgery or retraining. It also changes what HER and n-step replay can reconstruct. Curriculum should change the *content* within a stable schema: fill more rows as entities appear, activate more action candidates, goals, technology and map memory, and record stage/visibility as features if behavior depends on them. If a later stage truly exceeds measured 64-row recall or map extent, introduce a new schema version at a deliberate training boundary, convert retained raw snapshots where exact conversion is possible, and treat old checkpoints as initialization only after explicit compatibility checks. A model that sees easy and hard states under one layout can retain easy behavior and use mixed replay.

## Recommendation and migration

For the next live experiment, specify one stable `ObservationV3` contract: **32 by 32 one-tile fine grid; 16 by 16 eight-tile coarse grid with typed ore; at most 64 selected entity rows including player anchor; exact achieved/goal/tick; sparse inventory/flow/tech and explicit validity; and a small patch/frontier or complete-action-candidate sidecar when the task uses them**. Use named blocks and block encoders, with a compact replay representation that decodes to the learner's working precision only for sampled batches. Keep the PR #414 diff/cache wire and its cold/warm reset distinction. First test the representation on held-out ore/chest layouts and an L2 demonstration-seeded arm, then on an unseeded arm with improved complete-action admission; report success, selected-target recall, byte/RSS cost and update time at equal real transitions. A one-seed success cannot validate a full-open observation.

The migration is real: changing row cap alters `anchor` and `peer` head dimensions, masks, the schema fingerprint, replay array width and pointer batch shape (`fle/rl/schema.py:141-163,207-278`; `fle/rl/policy.py:173-188`; `fle/rl/replay.py:459-464`). The checkpoint loader rejects the new fingerprint and head sizes (`fle/rl/dqn_her.py:232-261`). A row-cap-only change leaves the shared row and pointer *weight shapes* intact, so an explicit weight-transfer experiment is possible, but the old replay and checkpoint cannot be loaded unchanged. A coarse-channel change also alters the first coarse convolution's weights. Preserve old artifacts for comparison. The raw entity/terrain protocol cache and static vocabulary can be reused; old flat observations cannot in general recover omitted patch/frontier or affordance facts, so they are not a clean V3 training dataset. If only one change is made first, set **64 entity rows**. It removes **62,720 bytes, or 40.7% of the current boundary**, cuts absent-row encoder work and pointer widths, and needs no new Lua signal. Its adequacy beyond the one-to-three-entity ladder is **UNVERIFIED**; log entity and action-target recall before increasing the cap. Then pack replay by type. This ordering tests the highest-cost assumption before undertaking the more involved typed replay and map redesign.
