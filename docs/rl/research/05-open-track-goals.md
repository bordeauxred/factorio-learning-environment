# Open-track goals and offline relabeling

This addendum changes the target from the stocked, quota-based PPO task in `docs/rl/DESIGN.md:1-5,121-123` to goal-conditioned open play with a replay-buffer learner. The hard contract is that every stored transition must contain enough information to evaluate `r(s,a,s',g')` for a new goal `g'` without a Factorio call. A goal is useful for Hindsight Experience Replay (HER) only when its achieved value `m(s)` is recoverable from the **stored observation**, not merely from a live server query or an unrecorded adapter accumulator. The current 14,177-float layout is a design, not an implemented RL adapter (`docs/rl/DESIGN.md:9-20,113-119`).

## 1. The open track

The task definitions distinguish three configurations. `open_play = DefaultTaskConfig(goal_description="Achieve the highest automatic production score rate", task_key=OPEN_PLAY)` has `task_type="default"` and declares 5,000 steps (`fle/eval/tasks/task_definitions/unbounded/unbounded_tasks.py:66-75,124-128`). `DefaultTask` installs an empty starting inventory, does not unlock all research, performs no extra setup, and always returns `success=False` from `verify` (`fle/eval/tasks/default_task.py:7-28,40-42`). Its wording says *rate*, but neither that class nor Gym computes a trailing-window rate. Gym's ordinary reward is the change in production score around the action, with an unconditional configured error-penalty subtraction (`fle/env/gym_env/environment.py:446-474`).

`open_play_production = UnboundedProductionTaskConfig(goal_description=_load_prompt(...), task_key=OPEN_PLAY_PRODUCTION, trajectory_length=5000)` is the Inspect open-play evaluation configuration. It also declares 60-second holdout and pre-holdout fields, but its Inspect solver scores the final trajectory rather than calling an item-throughput verifier (`fle/eval/tasks/task_definitions/unbounded/unbounded_tasks.py:86-114,130-135`; `fle/eval/inspect/integration/solver.py:707-715,1236-1251`). The prompt asks for the biggest automated factory and describes an economic production score (`fle/eval/tasks/task_definitions/unbounded/open_play_production.jinja2.md:1-11`). Its Inspect task lists both production and automated-production scorers (`fle/eval/inspect/eval_set.py:83-125`). The unbounded solver actually opens the Gym ID `open_play`, which uses `DefaultTask`, and runs `for step in range(trajectory_length)`; the Inspect ID `open_play_production` supplies metadata and the final scoring protocol (`fle/eval/inspect/integration/solver.py:707-735,762-767,833`). It records Gym `info["production_score"]` and `info["automated_production_score"]` after each action and the final automated scorer returns the final automated score, not a measured rate (`fle/eval/inspect/integration/solver.py:1034-1044,1236-1251`; `fle/eval/inspect/integration/scorers.py:440-456,500-528`). There is no quota success condition in this solver (`fle/eval/inspect/integration/solver.py:707-715,1211-1224`).

The distinct item-specific task is `iron_gear_wheel_throughput_unbounded = UnboundedThroughputTaskConfig(goal_description="Create an automatic iron gear wheel factory.", throughput_entity=Prototype.IronGearWheel, task_key=IRON_GEAR_WHEEL_THROUGHPUT_UNBOUNDED)` with 16 declared steps and 60-second holdout/pre-holdout settings (`fle/eval/tasks/task_definitions/unbounded/unbounded_tasks.py:27-30,35-48,117-122`). Its runtime class defaults to the populated lab-play inventory and all research unlocked (`fle/eval/tasks/unbounded_throughput_task.py:24-47`; `fle/eval/tasks/throughput_task.py:9-31`). After **each** action, `verify` repeatedly sleeps for a nominal 60 seconds, selects the greatest observed dynamic achievement for iron gear wheels, and returns `success=False`; its pre-holdout sleep is commented out (`fle/eval/tasks/unbounded_throughput_task.py:50-75`). It supplies achievement feedback but no reward override, so Gym still uses the production-score difference (`fle/eval/tasks/unbounded_throughput_task.py:70-75,93-103`; `fle/env/gym_env/environment.py:469-474`). This is an unbounded **target-item throughput** task, not free-form open play.

The unified registry contains all three keys, but maps only `default` and `unbounded_throughput` to `TaskABC` classes; `unbounded_production` is deliberately handled by Inspect, so `create_task("open_play_production")` is unsupported even though its key is discoverable (`fle/eval/tasks/task_definitions/unbounded/unbounded_tasks.py:138-156`; `fle/eval/tasks/task_definitions/task_registry.py:43-66,89-119`). The Gym registry registers every discovered key as an ID, including `open_play_production`, without checking that `create_task` supports it; making that ID through its factory would reach the unsupported-type error. Inspect avoids this by making `open_play` (`fle/env/gym_env/registry.py:36-54,77-83,112-113`; `fle/eval/inspect/integration/solver.py:726-730`). Declared trajectory lengths are runner budgets, not Gym truncation conditions (`fle/eval/inspect/integration/solver.py:833-833`; `fle/env/gym_env/environment.py:453-465,519-523`).

## 2. Score and achievements

The Lua production score prices items and fluids from resource seed prices and decomposable recipe ingredients, output amounts, and energy (`fle/env/tools/agent/score/server.lua:31-53,99-126,213-279`). For each force on surface 1, it computes each item's or fluid's **production-statistic input count minus output count**, multiplies that net count by its price, sums, then floors the total (`fle/env/tools/agent/score/server.lua:1-12,309-330`). The player score reported by `score()` subtracts a stored initial player score (`fle/env/tools/agent/score/server.lua:379-395`). Thus the implementation is a priced **net production/consumption balance**, not gross item output, inventory stock, a per-minute rate, or a monotone achieved-goal count. Its price list and final floor also discard the item-level information needed for item-specific HER (`fle/env/tools/agent/score/server.lua:309-330,391-408`).

`automated_score` starts from that total player score and subtracts the change in priced `storage.harvested_items` and the change in **net** priced manual crafting value, meaning crafted output value minus consumed input value; it floors the result (`fle/env/tools/agent/score/server.lua:335-376,386-408`). The harvest tool calls `stats.on_flow` and increments `storage.harvested_items` for its mined products; the craft tool records inputs and outputs and calls `stats.on_flow` for both (`fle/env/tools/agent/harvest_resource/server.lua:8-18,373-380`; `fle/env/tools/agent/craft_item/server.lua:112-127,186-203`). The harvested ledger is updated by the manual harvest tool in the searched environment code, not by a drill (`fle/env/tools/agent/harvest_resource/server.lua:8-18`; `fle/env/tools/agent/score/server.lua:335-345`). The Inspect scorer's comment that this subtraction includes resources gathered "by drills" is therefore at least misleading; whether every other manual acquisition route is accounted for is **UNVERIFIED** (`fle/eval/inspect/integration/scorers.py:424-437`). The score is a useful evaluation metric for factory value, but it is not a per-item automatic production vector and does not alone prove a particular item was produced by a machine.

Gym's `namespace.score()` returns `(production_score, automated_production_score)`; `info` exposes both cumulative values, while the step observation's `score` is the **step reward** and its `automated_score` is the cumulative automated value. At reset, a response-free observation sets both observation score fields to zero (`fle/env/tools/agent/score/client.py:11-25`; `fle/env/gym_env/environment.py:395-405,466-486,503-515,545-554`). The client additionally subtracts `instance.initial_score` from the returned player value when set, so baselines across Lua, client, and Gym need a live calibration before treating score deltas as an exact ledger (`fle/env/tools/agent/score/client.py:11-15`; `fle/env/instance.py:262-262,343-349`; `fle/env/gym_env/environment.py:545-547`).

`ProductionFlows` stores production/consumption dictionaries plus crafted and harvested records, without timestamps or an EMA; `get_new_flows` keeps positive differences and new craft records (`fle/commons/models/achievements.py:14-39,56-79`). The stats endpoint returns `output` from Factorio's `input_counts` and `input` from `output_counts`, despite confusing local names; the score tool identifies `input_counts` as produced, so `ProductionFlows.output` is the produced side used by achievements (`fle/env/tools/admin/get_production_stats/server.lua:10-39`; `fle/env/tools/agent/score/server.lua:1-11`; `fle/env/utils/achievements.py:27-40`). `calculate_achievements(pre,post)` calls harvested and hand-crafted outputs `static` and reports produced-count increases beyond those as per-item `dynamic`. It does this between two snapshots, not over a fixed time unless the caller supplies the interval (`fle/env/utils/achievements.py:7-40,43-63`). Gym takes pre/post stats each step and puts achievements in `info`; the item-specific task supplies a nominal 60-second interval by sleeping in `verify` (`fle/env/gym_env/environment.py:440-443,476-490,503-515`; `fle/eval/tasks/unbounded_throughput_task.py:55-75`). The live direction and completeness of these counters still require the known-drill/hand-harvest calibration already called for in the design (`docs/rl/DESIGN.md:83-85`).

## 3. Candidate goal spaces

The following shapes are **proposed** goal contracts. Pass means the stated *augmented stored observation* suffices for `m` and reward; current-layout failures are called out separately. Goal IDs must come from the pinned, checked-in `data/rl/vocab/factorio-2.0.73-base-v1.json` live export specified by the design, whose existence and live name/ID validation remain **UNVERIFIED** until implementation (`docs/rl/DESIGN.md:49-53`).

| Candidate | Exact `g`, `m(s)`, and reward | Offline verdict and failure mode |
|---|---|---|
| **Automatic production counts, recommended** | Four ordered items: `iron-ore`, `copper-ore`, `coal`, `iron-plate`. `g ∈ {0,…,64}^4` is an integer threshold vector with exactly one nonzero component in V0; `m(s)=min(64,(A_i(s))_{i=1}^4)`, componentwise, where `A_i` is episode-local automatic output after manual harvest/craft subtraction. For the active item `j` and quota `n=g_j`, use `r=[min(A'_j,n)-min(A_j,n)]/n + 1[A_j<n≤A'_j] - 0.001 - 10^-5·(tick'-tick)`. No success termination is needed. | **PASS after adding exact four counts and true tick to each stored observation**. The current proposal has only ore/plate production rows and clips/log-normalizes counts, so arbitrary four-item thresholds cannot reliably be recovered from it (`docs/rl/DESIGN.md:9-20,59,83-85`). Manual ledger omissions, counter resets, and a flat zero signal before first production remain risks (`fle/env/tools/admin/get_production_stats/server.lua:42-55`; `docs/rl/DESIGN.md:85-87`). |
| **Trailing production rates** | Same four-item ID order and `g ∈ {0,…,64}^4`, interpreted as items in the last 3,600 *true game ticks*. `m(s)=(ρ_i(s))_{i=1}^4`; use the same capped-progress/crossing reward with `ρ` in place of `A`. | **FAIL for an instantaneous factory snapshot or cumulative counters alone**: two identical current counters can have different last-minute production histories. The design's tick-stamped ring makes `ρ` a hidden-history quantity, and its current two-row production encoding is insufficient for four exact rates (`docs/rl/DESIGN.md:15-18,83-85`; `fle/commons/models/achievements.py:14-39`). **PASS only if** exact four-item trailing counts, window validity, and true tick are serialized in every observation; retain ring state for correct live updates and mark intervals longer than the window invalid (`docs/rl/DESIGN.md:83-85`). A short or incomplete window, output assigned to interval end, and a stopped line that still has recent output can mislabel success (`docs/rl/DESIGN.md:83-85,99-101`). |
| **Working structures** | `g=(k_drill,k_furnace) ∈ {0,…,8}^2`; `m(s)` counts distinct, force-owned burner mining drills and stone furnaces whose live status equals the exported `working` code. Reward is `Σ_i[min(m'_i,g_i)-min(m_i,g_i)]/max(1,Σ_i g_i) + 1[m(s)≱g and m(s')≥g]`. | **FAIL in the current 127-row entity view**: entities beyond selection cannot be counted, rich rows can be stale, and numeric status mapping is unverified (`docs/rl/DESIGN.md:13-14,55-59`; `fle/cluster/scenarios/open_world/observation_diff.lua:35-46,80-86,290-352`). **PASS with an exact, full-force two-count status summary stored in `s`**. A transient `working` status can fall when fuel runs out; many idle builds can game looser structural variants, and a count is not production (`fle/env/entities.py:48`; `docs/rl/DESIGN.md:89-95`). |
| **Spatial region** | `g=(r_x,r_y) ∈ {-16,…,16}^2` denotes a 16-tile region relative to spawn. `m(s)=(floor((x-x_spawn)/16),floor((y-y_spawn)/16))`; reward is `1[m(s')=g and m(s)≠g]`, optionally with a stored-coordinate distance-progress term. | **PASS if exact relative position or exact region ID is stored**. The proposed globals contain displacement divided by 128, while the diff header carries current character coordinates; exact region IDs avoid floating boundary errors (`docs/rl/DESIGN.md:18,59`; `fle/cluster/scenarios/open_world/observation_diff.lua:356-379`). It teaches exploration rather than factory production, and the map stream only covers generated chunks (`docs/rl/research/02-observation-space.md:75-75`). |
| **Technology completion** | In this order, use `automation`, `logistics`, `electronics`, `steel-processing`, `military`, `stone-wall`, `engine`, `landfill`, subject to live-vocabulary validation. `g∈{0,1}^8` is a requested researched bitmask and `m(s)∈{0,1}^8` is the force's completed mask. Reward is `Σ_i g_i(m'_i-m_i)/max(1,Σ_i g_i) + 1[m(s) does not cover g and m(s') covers g]` (`fle/env/game_types.py:313-349,435-440`). | **FAIL for the proposed RL observation**: the diff sends completion events and current research but not a complete researched mask, and the proposed per-step snapshot excludes a full scan (`fle/cluster/scenarios/open_world/observation_diff.lua:284-285,356-379`; `docs/rl/DESIGN.md:59`). **PASS if** a reset full-research snapshot plus every completion is maintained and the resulting eight bits are stored at each boundary. The existing full-state query can supply them but is an additional scan; `automation-science-pack` is pre-researched by reset, making that bit a trivial goal (`fle/env/tools/admin/save_research_state/server.lua:19-59`; `fle/env/tools/admin/reset/server.lua:72-82`). |

V0-open should use **automatic production-count goals** with the four-item allowlist above. It is small enough to query and store without a force-wide inventory scan, includes three raw extraction targets and one simple smelting target, and aligns with the existing per-item dynamic-achievement subtraction (`fle/env/utils/achievements.py:18-40`; `docs/rl/DESIGN.md:59,83-85`). Counts survive transfers and consumption, unlike inventory stock; their exact snapshot values make HER independent of the production history that produced them. The proposed item names are vocabulary keys, not new numeric IDs; a live export and counter-direction check gate implementation (`docs/rl/DESIGN.md:49-53,83-85`). An off-policy learner should store original and relabeled goals with its replay transitions; the exact discrete actor/critic architecture for the nine-head action space is **UNVERIFIED** (`docs/rl/DESIGN.md:22-35,113-115`).

## 4. Offline recomputability audit

For each replay transition store `(s_t, a_t, s_{t+1}, g, terminated, truncated)`, plus the original action outcome for diagnostics. Both observations must carry **exact** episode-local `A=(A_iron-ore,A_copper-ore,A_coal,A_iron-plate)`, componentwise capped at 64 only at serialization, and an exact integer elapsed `game.tick` relative to episode reset. Put the original four-threshold desired goal in the policy input and store it alongside each replay record. For HER, choose a future achieved count for one item that is strictly greater than that item's count at `s_t`, cap it at 64, set that one component of `g'`, and compute the formula in section 3 from `m(s_t)`, `m(s_{t+1})`, `g'`, and the two ticks. If no future positive increment exists, this trajectory supplies no positive production-count HER target. Because V0 continues to its fixed horizon after goal achievement, the relabeler does not need to invent an earlier terminal flag; preserve the real time-limit truncation. Store a separate `counter_valid` bit and exclude a transition or entire rollout if a raw/manual counter drops (`docs/rl/DESIGN.md:83-85`; `fle/env/tools/admin/get_production_stats/server.lua:42-55`).

The proposed observation already names an entity view, inventory, two per-item production rows, task fields, and an episode-tick global (`docs/rl/DESIGN.md:9-20`). It also proposes a paused batched query for raw production counters and manual ledgers and computes `A_i` in the adapter (`docs/rl/DESIGN.md:59,83-85`). **Missing:** `copper-ore` and `coal` production coverage, four exact integer-valued `A_i` lanes instead of relying on clipped/log-scaled rows, a four-threshold desired-goal input, exact true episode tick for the time term, and validity/reset markers. The existing `2×4` production rows are ore and plate only, and the `4` task fields encode a single target ID/quota plus budgets for bounded PPO (`docs/rl/DESIGN.md:15-18,59`). Thus the 14,177-float layout **fails the four-item HER contract as written**. A minimal new tensor contract can append four exact count lanes and one exact tick lane to the old state, and supply a separate four-lane goal vector to the policy and replay. The existing two rows can remain for auxiliary features. Counts `0..64` and an episode under 16,777,216 ticks are exactly representable as integer-valued float32; if longer runs are allowed, split ticks or store an integer side field. The resulting state has 14,182 floats before the four desired-goal lanes; this is a proposed layout, not an existing implementation (`docs/rl/DESIGN.md:7-20,59`).

The live computation still requires reset baselines for raw produced counts and manual harvested/crafted outputs, followed by their deltas at each paused boundary. Those baselines and ledgers are **not** functions of a single current game snapshot. The fix is to compute the episode-local `A_i` online once, serialize the resulting exact value into *every* observation, and record raw/manual counter endpoints and reset epoch as audit metadata; the offline reward reads only the serialized `A_i`, not the server or the metadata. This makes relabeling possible without claiming the environment is fully Markov. If per-item manual subtraction is wrong, replay faithfully reproduces a wrong signal, so compare the stored `A_i` with independent dynamic achievements on a known manual/automatic trace before training (`fle/env/utils/achievements.py:18-40`; `fle/env/tools/admin/get_production_stats/server.lua:10-39`; `docs/rl/DESIGN.md:83-85`). The proposed ring/window `ρ_i` is **not** needed for this reward; merely storing window fill is not enough to reconstruct it. `automated_score` is a priced scalar and cannot substitute for `A_i` (`fle/env/tools/agent/score/server.lua:309-330,397-408`; `docs/rl/DESIGN.md:15-18,83-85`).

## 5. Episode and reset structure

The current `DefaultTask.verify` and item-specific unbounded verifier never declare success; Gym initializes `terminated=truncated=False`, changes `terminated` only from task success, and has no trajectory-length or tick-limit check (`fle/eval/tasks/default_task.py:25-28`; `fle/eval/tasks/unbounded_throughput_task.py:50-75`; `fle/env/gym_env/environment.py:453-465,519-523`). Inspect's open-production solver stops at its own configured step loop unless Gym reports an ending or an error path intervenes (`fle/eval/inspect/integration/solver.py:833,1211-1234`). Gym runs `verify` before scoring and pauses after each action; with open play it does not perform a timed throughput check (`fle/env/gym_env/environment.py:453-474,519-523`).

**Proposed V0-open episode:** sample one of the four items uniformly and a quota uniformly from `{1,4,16}` at reset, encode it as a one-nonzero-component `g`, keep `g` fixed for the entire episode, and run at most **256 policy actions or 3,600 actual game seconds**, whichever occurs first. HER may relabel to any attained threshold up to 64. These are design parameters, not measured feasibility claims. Do not terminate on goal attainment; return `truncated=True` at the first budget limit, so HER can relabel later goals in one continuous trajectory. A catastrophic server failure invalidates the trajectory rather than counting as task success. At 60 ticks per game second, the time cap is 216,000 true ticks; at nominal 10× speed it represents at least six wall minutes of simulation before action, RCON, and UPS costs. Actual full-episode latency and whether 256 actions suffice for a from-scratch automated plate line are **UNVERIFIED** (`fle/env/gym_env/registry.py:184-193`; `fle/env/instance.py:124-135`; `docs/rl/DESIGN.md:162-166,190`). Track genuine goal-reaching frequency separately from HER-relabeled success.

Reuse an already running server across episodes. `make_factorio_env` attaches to a container, constructs an instance, sets speed 10, calls `task.setup`, and then wraps Gym; the Inspect solver separately calls `gym_env.reset()`, so the open-play path already performs setup reset and another Gym reset (`fle/env/gym_env/registry.py:112-145,177-193`; `fle/eval/tasks/task_abc.py:61-68`; `fle/eval/inspect/integration/solver.py:762-767`). Instance construction uploads/loads scripts, initializes a character, and forces chunk generation around origin; those cold operations should be amortized, with startup time measured separately (`fle/env/instance.py:222-244,511-544,573-595`). Gym reset calls `instance.reset`, which resets namespaces, clears production stats, regenerates resources, clears entities, sets inventory, and resets research on the existing server; it does **not** restart the container (`fle/env/gym_env/environment.py:525-554`; `fle/env/instance.py:287-325`; `fle/env/tools/admin/reset/server.lua:21-32,36-56,61-99`). Reset defaults `reset_position=False`; V0-open must request origin repositioning or explicitly restore a known spawn, and must replace client diff caches/full-sync and rebase counters at each reset (`fle/env/instance.py:287-316`; `fle/env/tools/admin/reset/server.lua:44-56`; `docs/rl/DESIGN.md:117-119`). `regenerate_resources` scans all resource entities on the surface and assigns large amounts, so reset cost can grow with explored map area; reset does not erase generated chunks (`fle/env/tools/admin/regenerate_resources/server.lua:1-13`; `fle/cluster/scenarios/open_world/observation_diff.lua:455-473`). Its wall cost is **UNVERIFIED**. Keep one seed per reused container; `Gym.reset(seed)` ignores its argument and a new map seed is selected at container launch, not by this reset (`fle/env/gym_env/environment.py:533-545`; `fle/cluster/run_envs.py:100-119`; `docs/rl/DESIGN.md:121-123`).

## 6. What open play makes harder

| Problem and severity | Evidence and cheapest mitigation |
|---|---|
| **Bootstrap from empty inventory: critical.** | Open play sets `{}` and research false, and reset clears items before inserting that empty dictionary. The stocked throughput task supplies drills, furnaces, belts, coal, and all research (`fle/eval/tasks/default_task.py:15-21`; `fle/env/tools/admin/set_inventory/server.lua:1-10`; `fle/eval/tasks/throughput_task.py:9-31,50-56`). The existing PPO head has `PLACE` but no `CRAFT`, `SET_RECIPE`, or `RESEARCH`; it therefore cannot build a drill from an empty start as specified (`docs/rl/DESIGN.md:22-35`; `fle/eval/open/MANUAL.md:36-48`). Cheapest fix: implement a minimal bootstrap macro sequence/action set for mining, smelting, and crafting before claiming open-play feasibility, then prove one scripted empty-start automatic-ore trajectory. |
| **State growth and UPS: high.** | The proposed policy sees 127 selected real entities, while the diff cache/full sync and reconcile sweep can grow with the entire force factory; the terrain sync iterates generated chunks. At scale the benchmark source measures both poll latency and UPS, and prior research reports UPS falling with thousands of entities; the V0-open performance is **UNVERIFIED** (`docs/rl/DESIGN.md:13-14,55-59`; `fle/cluster/scenarios/open_world/observation_diff.lua:290-352,430-473`; `tests/benchmarks/benchmark_stress.py:122-147`; `docs/rl/research/02-observation-space.md:79-89`). Cheapest mitigation: enforce the 256-action/one-hour cap, retain priority-stratified entity selection, log selected-relevant fraction and full-sync count, and measure UPS at 100/1,000/5,000 entities before scale-up. |
| **Long, sparse credit chain: critical.** | Even stocked ore needs drill placement and fueling before `A_ore>0`; the design calculates a very small illustrative random two-action probability, and the open start additionally needs manual collection, smelting, and crafting (`docs/rl/DESIGN.md:85-87`; `fle/eval/open/MANUAL.md:5-34,36-48`). Cheapest mitigation: start with the raw-ore goals and a short scripted/demonstration replay seed, then test whether HER produces any future positive-count relabels. No amount of HER creates a positive production future from all-zero trajectories. |
| **Resource discovery, exhaustion, and map dependence: high.** | The open-world stream observes generated chunks but does not explore for the agent; reset regenerates resource amounts to 10,000 or 300,000 rather than returning a pristine map, and the default reset does not reposition the character (`docs/rl/research/02-observation-space.md:75-75`; `fle/env/tools/admin/regenerate_resources/server.lua:1-13`; `fle/env/instance.py:287-316`). Cheapest mitigation: fix spawn and seed per container, include explore/move actions and exact relative position, cap time, and compare early-goal success across held-out map seeds. |
| **Irreversible mistakes and partial mutations: high.** | Gym detects errors by text, while the design notes tool failures can mutate the world before error; the new policy cannot assume a failed place/harvest leaves the state unchanged (`fle/env/gym_env/environment.py:446-451`; `docs/rl/DESIGN.md:79-79`). Cheapest mitigation: always pause and re-observe after failures, record actual next state in replay, keep recovery/pickup actions, and reject counter-reset episodes. Do not restore a pre-error observation as if it were the successor (`docs/rl/DESIGN.md:79-79,83-85`). |

## 7. Top five risks and resolving experiments

1. **The purported automatic counter may include manual output or use the wrong stats direction.** The raw stats endpoint has contradictory local names, while the score and achievement paths imply Factorio `input_counts` means production (`fle/env/tools/admin/get_production_stats/server.lua:14-39`; `fle/env/tools/agent/score/server.lua:1-11`; `fle/env/utils/achievements.py:18-40`). Cheapest experiment: in one later approved live probe, separately hand-mine, hand-craft, run a drill, and run a furnace; compare raw counters, manual ledgers, `A_i`, and dynamic achievements before any learning.
2. **HER may produce no useful positive relabels.** Empty-start play needs craft/smelt/build actions that the current PPO action list omits, and production progress is zero before the first working machine (`fle/eval/tasks/default_task.py:15-21`; `docs/rl/DESIGN.md:22-35,85-87`). Cheapest experiment: record one scripted empty-start automatic-ore trajectory, run the offline relabeler over it, and report fraction of transitions with a strictly larger future achieved count; then compare with unassisted exploratory traces.
3. **Observation encoding can silently break offline reward equality.** The existing layout has only two log-scaled/clipped production rows and no four-item exact `A` vector; the rate ring and counter baselines live outside the observation (`docs/rl/DESIGN.md:15-20,59,83-85`). Cheapest experiment: after implementation, serialize a short recorded trace, discard the live environment, recompute original and hundreds of relabeled rewards from stored `s,a,s',g` only, and compare original-goal values bit for bit with online reward logs.
4. **Long episodes may be too expensive or the entity view may omit needed machines.** Open tasks declare 5,000 steps, the proposed view retains 127 real entities, reconcile work grows with tracked entities, and server UPS falls in the reported stress work (`fle/eval/tasks/task_definitions/unbounded/unbounded_tasks.py:69-71,96-101`; `docs/rl/DESIGN.md:55-59`; `fle/cluster/scenarios/open_world/observation_diff.lua:290-352`; `docs/rl/research/02-observation-space.md:79-89`). Cheapest experiment: once live evaluation is allowed, measure full 256-action episode wall time, reset time, UPS, and selected-relevant fraction at three factory sizes, with no learning run.
5. **Replay validity can fail across reset or hidden history.** Reset clears stats and manual ledgers, but generated chunks and default character position can persist; the proposed trailing rate depends on a ring, not a single current factory snapshot (`fle/env/tools/admin/reset/server.lua:21-56`; `fle/env/instance.py:287-316`; `docs/rl/DESIGN.md:83-85`). Cheapest experiment: run two short episodes on one reused server, verify an episode/reset epoch and `A=0` at each start, test counter-drop rejection, and ensure every relabeled goal/reward uses only transitions within one epoch.
