# Rethinking the RL action space after the live ladder

The next action interface should be a **small, state-dependent set of complete macro-action candidates**, with one Q score per candidate and an operation-aware candidate generator. Keep the existing stable vocabulary IDs and exact-action dispatch contract. Do not make a larger independent-head policy the next experiment. A candidate set can rule out definite tuple errors before selection, and Double DQN can maximize exactly over the candidates it actually offers. Placement and routing will still need server validation. This recommendation is about the agent's choice set, not a claim that masks alone solve sparse reward.

## What the evidence establishes

The live ladder used one training seed and map 44340, with fresh greedy evaluation and exploration off. L0 was 32/32 trained versus 16/32 random, L1 was 32/32 versus 1/32, and L2 was 0/24 versus 0/24. L2 became 32/32 after 96 real scripted transitions seeded replay. The successful trace was `PLACE → INSERT → WAIT` (`docs/rl/results/ladder.md:13-38`, `docs/rl/results/ladder.md:69-89`, `docs/rl/results/ladder.md:117-131`, `docs/rl/results/ladder.md:194-215`). L1 shows the learner can discover a useful entity and item choice when the machine already exists. L2 adds a location, orientation, prototype and a three-action dependency. It does not isolate action factorization as the only reason for failure: the no-demonstration run had no assigned-goal successes and almost no positive HER signal (`docs/rl/results/ladder.md:142-180`).

The action interface nevertheless failed directly. The no-demonstration L2 checkpoint chose invalid `CONNECT` tuples in all 384 final greedy decisions. A local `CONNECT` mask correction left the same checkpoint choosing `RESEARCH(technology=0)` in all 384 decisions. The latter was first logged as a tool failure and then, after preflight classification was corrected, as a preflight-invalid tuple; its behavior and reward did not change (`docs/rl/results/ladder.md:166-175`, `docs/rl/results/ladder.md:261-289`). The training preflight-invalid rate was 813/2,029 non-WAIT decisions, or 40.07%, without demonstrations and 308/1,100, or 28.00%, with them. Both exceed the design's 15% concern level. The 5.90% random-baseline rate is not a clean control for the learned policy: that baseline samples an operation first and calls operation-conditional argument masks, while the learner uses state-only masks (`docs/rl/results/ladder.md:240-257`, `tests/benchmarks/run_ladder.py:66-69`, `fle/rl/dqn_her.py:150-172`). The old-run invalid rate is also a lower bound on semantic invalidity because some sentinel failures were initially classified as tool failures (`docs/rl/results/ladder.md:274-289`).

## Why the current decomposition collapses

The implemented score has the form

`Q(s,a) = V(s) + A_op(s,op) + mean_{h active for op} A_h(s,a_h)`,

with each head advantage centered over its state-only mask (`fle/rl/policy.py:179-188`, `fle/rl/policy.py:203-225`). The schema declares required heads by operation, but index 0 is always enabled for every argument head (`fle/rl/schema.py:15-17`, `fle/rl/schema.py:191-204`, `fle/rl/masks.py:32-39`). Thus `RESEARCH` and `technology=0` are separately mask-legal although their combination is not. `plan_action` rejects it before executing research (`fle/rl/action.py:38-44`, `fle/rl/action.py:115-118`). The same issue applies to `CONNECT` with a missing connection type, `INSERT` with player anchor 0, and entity-item or placement combinations that individual marginal masks cannot express (`fle/rl/action.py:62-73`, `fle/rl/action.py:119-143`, `fle/rl/masks.py:63-65`).

For an invalid tuple that preflight rejects, the environment usually returns no effect on the intended machine and no goal progress. The TD error is **not zero**. It updates the shared value, selected operation advantage and selected active argument advantages; each selected argument receives a share through the active-head mean. Centering also couples each selected value to the other currently unmasked values. But when changing one argument still yields the same invalid result, the data supplies no outcome difference saying which argument would have made the operation work. The learner can push observed invalid choices down, yet the split of blame across op and arguments is underdetermined. Unexecuted valid combinations have no direct target at all. An additive Q cannot represent a specific useful `PLACE(prototype,site,direction)` conjunction or a specific `INSERT(entity,item)` compatibility table unless its factors happen to make that conjunction rank high. Repeated bootstrapping through invalid next actions can reinforce arbitrary extrapolation from those poorly covered combinations (`fle/rl/dqn_her.py:191-213`). This is an identifiability and coverage problem, not merely a missing penalty.

There is a second, more exact error in action selection. `greedy_tuple` chooses each head's argmax and then zeroes inactive heads. It chooses `op` from `A_op` alone; it does not compare the full scores of the best valid completion of each operation (`fle/rl/dqn_her.py:36-58`). Therefore it need not maximize even the Q function implemented by `score_tuple`. Double DQN evaluates that independently selected tuple with the target network, including when it is invalid (`fle/rl/dqn_her.py:52-58`). A valid but bad placement is more useful data: it may create a machine, occupy a tile, consume inventory, advance production by two rather than four, or expose a wrong output orientation. In the demonstrated L2 run the first periodic greedy policy placed and fuelled a drill but stalled at two ore because the output missed the chest (`docs/rl/results/ladder.md:225-230`). That transition distinguishes spatial quality. A preflight-invalid tuple never tests its purported placement or transfer, consumes a decision, and can produce a nearly featureless self-loop. Actual ticks can still pass, so it is not literally a zero-cost or identical transition (`docs/rl/research/01-action-space.md:76-80`).

## Candidate interface to build next

At each paused observation boundary, generate complete actions from the information already held. A candidate is a full schema tuple plus a stable identity and a feasibility label. `WAIT` supplies its four durations. `RESEARCH` supplies one action per enabled, unresearched technology with met prerequisites, never sentinel 0. `INSERT` and `EXTRACT` supply only selected real entity rows paired with relevant held items and quantities that have local slot support. `PLACE` supplies inventory-backed prototypes paired with nearby candidate centers, legal center parity and orientations. For the L2 stage, include candidate positions over observed ore within build reach and surrounding transfer positions; do not encode map 44340 or the scripted `(106,-128)` answer. `CONNECT` supplies only distinct supported endpoints with material and coarse connector compatibility. MOVE and HARVEST use observed local targets. The generator should be deterministic from a versioned boundary snapshot and should cap each family with a measured candidate-recall diagnostic. The current flat observation carries marginal masks and summarized entity inventories, not all pairwise affordances needed to regenerate that set (`fle/rl/schema.py:218-259`, `fle/cluster/scenarios/open_world/observation_diff.lua:150-156`). Store the compact candidate list or its sufficient inputs alongside each replay boundary, including the successor boundary. The full selected tuple remains in replay; an index into an ephemeral list alone is insufficient. Keep old invalid-tuple replay out of the new admissible-action training comparison.

First fix admission and selection together: generate only locally supported complete tuples, score each complete tuple, select the highest online score, and have the target network evaluate that same tuple. For a finite offered set `C(s)`, `max_{a in C(s)} Q(s,a)` is exact over `C(s)` and defines an ordinary Bellman target for the restricted MDP. The stored `C(s')` must agree with what acting would have offered at that successor boundary; any cap or heuristic ranking becomes part of the policy's action space and needs recall measurement. Use the current state encoder, entity row embeddings and stable catalogs. A complete-action scorer should receive operation, selected entity embeddings, item/prototype/recipe/technology embeddings, relative location, direction and relevant pair features. A small interaction MLP can then represent that coal belongs in this drill and that this drill orientation feeds this receiver. The existing additive branch scorer can be a short admission-only ablation, but it cannot model those interactions. This adds candidate generation, replay sidecar storage, variable-length batching and scorer inference proportional to offered candidates; it does not require a dense head over all Factorio action tuples.

For the immediate L2 experiment, stage-mask operations and arguments to the needed families, including `PLACE`, `INSERT`, `WAIT` and any movement needed to reach a site. Keep stable catalog IDs and checkpoint schema widths; stage masks narrow availability without remapping IDs. The design currently seeds curriculum goals but explicitly does not restrict action vocabularies (`docs/rl/DESIGN.md:105-107`). On a 16-decision task whose successful behavior uses three operations, making all 12 operations compete is an avoidable exploration cost. Retain easy goals during expansion, then unlock CRAFT, SET_RECIPE, CONNECT and RESEARCH as tasks require them. This is a curriculum over affordances, not a hard-coded solution trace.

Measure two things separately. First, require preflight-invalid combinations below 5% of non-WAIT decisions, with zero required-head sentinel choices in fresh greedy evaluation, while reporting tool rejection and partial mutation separately. Second, at matched fresh environment transitions and no demonstrations, compare L2 assigned-goal success, valid `PLACE` frequency, useful drill placement frequency, and time to first positive automatic ore against the 0/24 checkpoint; repeat across several training and map seeds before a general claim. Keep a demonstration-seeded arm so the interface is also tested when reward is available. If invalidity falls but no-demonstration L2 still has no assigned successes, the mask change worked and sparse reward or exploration remains the binding problem. If useful placements remain rare despite low invalidity, inspect candidate recall and joint-Q ranking. The current one-seed 28-40% rates are already enough to justify the structural change, even though they do not satisfy the design's former 10,000-transition, three-seed trigger (`docs/rl/DESIGN.md:79-81`, `docs/rl/results/ladder.md:254-257`).

## Alternatives and their costs here

| Approach | What it buys | Cost or failure mode in FLE |
|---|---|---|
| Autoregressive heads | Sample `op`, then condition target/position, item or prototype, and remaining arguments on the prefix. Every sampled prefix can get a conditional mask. This is close to the design's proposed interaction head (`docs/rl/DESIGN.md:115-117`). | A product policy is well defined, but Q-learning still needs a max over complete actions. Sequential greedy head choices generally do not maximize a joint Q; exact search is exponential in the coupled choices, so use beam search or a finite candidate set. The Double DQN online selector and target evaluator must use the same search rule and legal completions. A beam target is a defined approximate control target, not the unrestricted Bellman optimality maximum. Ordering also matters: for PLACE, prototype before site may be useful; for INSERT, entity before item may be useful. |
| Conditional masks on the present branches | Operation-first masks immediately remove `technology=0`, missing connection types and unused anchors, with little network change. Pair-conditioned masks remove entity-item and source-peer mismatches. The random baseline already uses the operation-only form (`tests/benchmarks/run_ladder.py:66-69`). | Merely masking each branch after choosing `op` still inherits the additive Q's missing pair interactions and the operation selection error. To choose `op` correctly, compare complete supported completions per op. At that point sparse candidates are the clearer interface. |
| Merge heads | The existing 290-way offset head is sensible: 289 spatial offsets plus sentinel prevent impossible independent x/y choices (`fle/rl/schema.py:141-163`). An `op × item` head is 12 × 253 = **3,036** cells. | `anchor × prototype` is 512 × 105 = **53,760** cells, `anchor × item` is **129,536**, and `anchor × peer` is **262,144** before connector type. A full nominal PLACE choice is 512 × 104 non-sentinel prototypes × 289 offsets × 4 directions = **61,554,688** combinations. `op × item` does not decide which entity accepts an item. Dense joint heads spend parameters on absent rows and impossible pairs; enumerate sparse supported pairs instead. |
| Pointer-first or spatial maps | `entity → operation → admissible item/recipe/peer` naturally fits INSERT, EXTRACT, PICKUP, ROTATE and SET_RECIPE. A grid-site pointer plus type/orientation, analogous to spatial action maps in SC2LE or AlphaStar, fits PLACE and HARVEST. Shared entity and spatial encoders can generalize across row identities and map positions (`docs/rl/DESIGN.md:111`). | Neither ordering covers every op. RESEARCH has no entity; CONNECT needs two endpoints and a route; a spatial cell alone cannot encode what to insert or whether a belt route exists. A heterogeneous candidate set can use entity pointers and spatial-site proposals as generators, without forcing one universal action grammar. |
| Stage-specific operation and vocabulary masks | Greatly reduces exploration entropy at L0-L2 while keeping the full pinned IDs. Growth can be tied to observed success and prerequisite capability. | Success on a small stage does not show open-world competence. Over-pruning can hide alternate solutions or necessary preparatory actions. Log candidate recall against scripted and exploratory successful traces, and test held-out layouts. |
| Options or hierarchical actions | A later `establish ore line` option could internalize PLACE, fuel, output alignment and WAIT, shortening long-horizon tasks. | It shifts learning into option policy and termination, obscures the exact placement choices at issue, and makes partial mutations and tick accounting harder. Three primitive actions suffice for live L2 when demonstrated, so an option is premature as the first fix (`docs/rl/results/ladder.md:194-215`). |

The cardinalities above are head sizes from the checked-in Factorio 2.0.73 base artifact: 104 placeable prototypes plus sentinel, 251 item names plus PAD/OTHER, 217 recipe names plus PAD/OTHER, and 196 technologies plus sentinel. Their current dimensions are `op=12`, `anchor=peer=512`, `prototype=105`, `item=253`, `recipe=219`, `technology=197`, `offset=290`, `direction=5`, `connection=4`, `quantity=5`, and `duration=5` (`data/rl/vocab/factorio-2.0.73-base-v1.json`, `fle/rl/vocabulary.py:316-336`, `fle/rl/schema.py:86-108`, `fle/rl/schema.py:141-163`). These are pinned-artifact counts, not universal Factorio counts. The full `op × item` number includes combinations where the op ignores item; useful sparse choices are much fewer.

## Mask contract and server information

Define legality at two levels. **Admission** must exclude definite invalidity under the held state: required sentinel arguments, missing selected rows, unsupported tool prototypes, incompatible entity-item pairs, identical CONNECT endpoints, unavailable connector material, disabled research and invalid center parity. For any admitted partial choice in a sequential generator, at least one complete action must survive these *known* constraints. This is the useful support property. Ordinary pairwise arc consistency alone does not guarantee a globally consistent tuple when three or more arguments interact; the generator should filter complete candidates or use forward checking. Irrelevant heads may still serialize as 0 after a complete action is chosen. **Execution validity** remains server-owned for reach, collisions, routes, races and mutable inventories. Do not call an uncertain action proven valid. Track `known-valid-locally`, `uncertain`, `preflight_invalid`, `tool_rejected` and `partial_mutation` separately.

The cost of exact global support is unacceptable as one RCON probe per possible tuple. Section 4 of the action-space research records a `can_place_entity` call per prototype, direction and position, 2+ calls for movement pathing, and compound route work for CONNECT (`docs/rl/research/01-action-space.md:58-74`). Even the 28-entity V0 allowlist across 289 offsets and four directions implies up to **32,368** placement probes per anchor before duplicate sites or reach filtering (`docs/rl/DESIGN.md:75`). One batched Lua call would remove network round trips but still performs that many game checks. Use static metadata, current inventory, cached terrain, footprint occupancy, reach bounds and only nearby task-relevant sites for a cheap first pass. For uncertain high-ranked candidates, a chosen-action server check can be worthwhile; it should not silently relocate the action. This contract is approximately complete over useful local actions, with explicit candidate recall, rather than falsely promising exact world-valid masks.

The Lua side could make that first pass substantially better with a compact, same-boundary **affordance delta**. For each selected entity, expose its live type, recipe, burner/fuel compatibility, actual slot kinds and contents, capacity or fullness, and accepted items intersected with the player's currently held item kinds. Compute accepted-item support using the same rules as `insert_item`, not merely generic `entity.can_insert`, because the tool has type-specific fuel, lab, assembler, furnace and module branches (`fle/env/tools/agent/insert_item/server.lua:68-161`). The current diff exports some inventory rows and recipe names but no accepted-item relation or slot-capacity relation (`fle/cluster/scenarios/open_world/observation_diff.lua:109-156`). An all-items-by-all-entities acceptance matrix would cost too much and would mostly encode unused items; sparse lists for selected entities and held kinds are the useful unit. Exact agreement between such a new predicate and tool execution is **UNVERIFIED** until tested, particularly where the tool searches for a nearby substitute or mutates after validation.

For PLACE, Lua could return a bounded list or bitmap of buildable candidate centers and orientations for prototypes actually in inventory near the player or task focus. A single batch can call `surface.can_place_entity` using the same intended exact center, direction, force and reach checks as the placement tool, while also reporting resource overlap and output-port geometry. The first bits describe current buildability; the latter features help the critic distinguish a drill that feeds the chest from one that stalls at two ore. The server's placement path already uses a surface check and has special behavior for some prototypes (`fle/env/tools/agent/place_entity/server.lua:193-229`, `docs/rl/research/01-action-space.md:54-68`). Batch size, Lua CPU cost, cache invalidation after construction and exact agreement with `place_entity(..., exact=True)` are **UNVERIFIED**. Start with local geometry and a small proposed-site batch, not an exhaustive action mask. Similarly, expose compatible endpoint/port types for CONNECT, but leave route feasibility to its router; research eligibility already has enough state to avoid new per-tech queries (`docs/rl/research/01-action-space.md:73-74`).
