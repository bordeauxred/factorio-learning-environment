## 1. PR414 protocol

The public RCON functions are `obs_diff_drain`, `obs_terrain_drain`, `obs_all_drain`, and the two `*_full_sync` functions. An entity drain always starts with `h<tick>:<current-research-name|->:<integer-percent>:<character-x>:<character-y>`; its following semicolon-separated records are `u<unit-number>,<rich-row>`, `r<unit-number>`, `q<finished-tech-name>`, or `!overflow`. A terrain drain is a semicolon-separated record string, empty when unchanged. `obs_all_drain()` combines the entity part and terrain part with one `~` in a **single RCON response**, and clears both buffers. The two full-sync functions reset their corresponding **server-side** buffers/state and return a snapshot; the terrain full sync iterates every generated chunk, so it is a cold-attach/recovery operation, not a steady-step operation [fle/cluster/scenarios/open_world/observation_diff.lua:23-39,391-473]. The buffer cap is 50,000 records per tier; overflow requires full sync, and the clients only flag it, rather than recovering automatically. Applying a full snapshot to a populated `TieredClient` does not first clear its old dictionaries, so correct recovery must explicitly replace/reinitialize client state before applying a snapshot [fle/cluster/scenarios/open_world/observation_diff.lua:41-46,68-78,430-460; tests/benchmarks/benchmark_tiered_obs.py:32-85; tests/benchmarks/benchmark_tensor_obs.py:310-314,419-421].

| Tier | Trigger and exact records |
|---|---|
| Terrain | `on_chunk_generated` encodes each 32×32 chunk: `c<cx>:<cy>:<waterhex>` (32 rows of eight hex digits; empty means all land), `o<resource-name>:<tile-x>:<tile-y>:<floor(amount/100)>`, `t<x>:<y>` tree, `k<x>:<y>` rock/cliff, and `n<unit>,<enemy-name>,<x>,<y>` spawner/turret. Only four named water variants are included [fle/cluster/scenarios/open_world/observation_diff.lua:43,48,187-238,244-248]. |
| Structural | Build/robot build/script build/revive/clone/rotate enqueue `u`; mining, death, and script destroy enqueue `r` for player entities, `x<x>:<y>` for trees/rocks/cliffs, or `m<unit>` for enemy structures. Resource depletion emits `d<x>:<y>`; research completion emits `q<name>` [fle/cluster/scenarios/open_world/observation_diff.lua:250-286]. |
| Drift | Every 47 game ticks the Lua re-rows up to 50 tracked entities; every 32 such passes it scans player-force entities for creations without an event. It rescans up to four tracked resource chunks per pass, emitting `o` when an amount bucket changes and `d` when a tile disappears. Latency therefore grows with tracked entity/resource-chunk count; it is not a fixed 47-tick freshness guarantee [fle/cluster/scenarios/open_world/observation_diff.lua:41-45,290-352]. |
| Hot fields | Each `u` row starts `name,x,y,direction,status`. Optional tags are `E<floor(joules)>`, `P<floor(crafting_progress×100)>`, `R<recipe-name>`, `H<floor(health)>`, `W<tile-width>:<tile-height>`, `D<drop-x>:<drop-y>`, `K<pickup-x>:<pickup-y>`, `N<electric-network-id>`, `T<floor(temperature)>`, repeated `I<inventory-index>.<item-name>:<count>` from inventory indices 1–4, and repeated `F<fluid-name>:<floor(amount)>`. The emitted row has these values, but an upsert is gated by a signature with MJ energy, progress deciles, health/50, temperature/25, and `log2` item/fluid count buckets. Direction, status, recipe, footprint, pickup/drop coordinates, and network ID enter the signature directly. Thus a cached exact count is only exact **at its last emission**, not necessarily at the current tick [fle/cluster/scenarios/open_world/observation_diff.lua:63-65,80-170,321-325]. |

`TieredClient` stores full client-side dictionaries/sets for unit-keyed entity rows, chunk water masks, **named** ore tiles, trees, obstacles, nests, the header fields, and completed-tech events [tests/benchmarks/benchmark_tiered_obs.py:14-85]. `TensorClient` subclasses it and keeps an incremental additive `(17,96,96)` float32 grid of 3-tile cells, a `(10,)` global vector, an absolute `(2048,38)` table and `(2048,)` occupancy mask, then returns a fixed `(view_k,38)` nearest-first player-relative view and view mask (`view_k=2048` by default). It subtracts an entity's old cell contribution before applying the new row, tracks water/ore contributions separately, recenters the grid after a 24-tile dead zone, and can rebuild from its dictionaries. Table slots are stable during incremental updates, but the nearest-view order and full-rebuild slots are not. A full table marks overflow; its top eight item pairs are per-entity **merged inventory** slots, not player inventory [tests/benchmarks/benchmark_tensor_obs.py:44-113,115-130,198-275,277-314,319-421,437-513]. Current grid channels are five named entity types plus other, status **sum**, direction sine/cosine sums, MJ energy, progress, log2 inventory total, water, trees, rock/cliff, a **single ore bucket sum**, and enemy structures. Global fields are tick/1e6, research percent, counts of entities/ores/trees/nests/completions, overflow, and **raw absolute player x/y** [tests/benchmarks/benchmark_tensor_obs.py:14-26,44-59,198-214,424-435].

This client is **benchmark-only**, located under `tests/benchmarks/`, with an explicit `sys.path` insertion and import of another benchmark module; the protocol tests import the benchmark the same way. It is not supported `fle/` library code. Lifting it means packaging both client classes and their record parser, defining a stable item/entity/recipe/tech vocabulary and overflow/full-sync lifecycle, replacing the current 17-channel/38-feature tensorizer with the V0 shapes and normalizations, and integrating the drain with an RL environment. Its current runtime dependencies are NumPy, Python standard-library math, and `TieredClient`; the benchmark `main()` additionally needs `factorio_rcon`, an RCON server, and benchmark-specific setup. The source module imports `factorio_rcon` at import time, so that dependency must be declared or removed from a library extraction [tests/benchmarks/benchmark_tensor_obs.py:31-43,86-113,516-525; tests/benchmarks/benchmark_tiered_obs.py:7-15; tests/observation_diff/test_tiered_protocol.py:7-32].

The live tests pin API existence, terrain startup, advancing header tick, build/remove events, authoritative entity identity/position, eventless direction and creation recovery, sparse hot updates, ore depletion, tree removal, new-chunk streaming, full-sync structural consistency, incremental-grid equality, exact delivered entity position/count and interlink fields, top-eight truncation, slot stability, recentering, and nearest-K selection. They **do not pin** the proposed 12/6 channels, per-ore channels, complete technology bitmask, flow rates, player inventory, status-to-name mapping, stratified K, normalization, overflow recovery, or lab-scenario operation [tests/observation_diff/test_tiered_protocol.py:92-111,114-118,140-177,180-238,241-285,296-324,327-418,421-488; tests/observation_diff/conftest.py:47-68,110-115].

## 4. Production flows

`ProductionFlows` is a data holder for `input`, `output`, `crafted`, `harvested`, and optional pricing/static-item fields. `get_new_flows(pre, post)` subtracts cumulative dictionary values and keeps positive differences; it has **no time-window or rate calculation** [fle/commons/models/achievements.py:14-79]. In `FactorioGymEnv.step`, FLE calls `_get_production_stats()` before and after action execution, converts both snapshots, and places their positive difference in `response.flows`; `get_observation(..., response)` reuses that difference, while reset/direct observation fetches another snapshot. Thus gym step flows are **per-action-interval count deltas**, with whatever game ticks the action consumed, not items/minute. The interval varies by action and game speed; `Observation.to_dict()` labels those values `rate`, but performs no division by elapsed ticks [fle/env/gym_env/environment.py:329-334,440-490; fle/env/gym_env/observation.py:113-139,210-220].

The server tool obtains `force.get_item_production_statistics(surface)` and `get_fluid_production_statistics(surface)`, reads full `input_counts`/`output_counts` tables, loops over every key, and includes harvested/crafted storage. It returns `output = consumption_diff` and `input = production_diff`, while assigning `consumption_diff` from `*_input_counts` and `production_diff` from `*_output_counts`. The local variable names and returned key names point in opposite directions; which returned key actually denotes production is **UNVERIFIED** without confirming Factorio's `input_counts`/`output_counts` semantics. It is a separate `Tool.execute` RCON round trip with Lua table serialization/parsing; the actual wall time and stats-table size are **UNVERIFIED** [fle/env/tools/admin/get_production_stats/server.lua:1-39; fle/env/tools/admin/get_production_stats/client.py:4-12; fle/env/tools/controller.py:207-234].

Items/minute is derivable as `delta_count × 3600 / delta_game_ticks` for a chosen rolling game-tick window (assuming 60 game ticks per game-second, as the gym code does), after validating production/consumption key direction. The repo does not implement that window. At short windows, discrete craft/mining events imply many zeros and occasional spikes; variable action duration and manual crafting/harvesting further alter interpretation. Quantified variance is **UNVERIFIED**. `stored` is not a production-stat counter; it needs a separately defined stock measure (player only, selected entity inventories, or force-wide inventory) [fle/env/gym_env/environment.py:323-326,440-490; fle/env/tools/admin/get_production_stats/server.lua:14-39; fle/env/gym_env/observation.py:215-220].

## 5. Technology

The existing `save_research_state()` tool scans `pairs(force.technologies)` and serializes every technology's name, researched/enabled bits, level, research-unit cost/energy, prerequisites, and ingredients. It also returns current research name/progress and research queue. It is **one additional RCON call** whenever invoked, with an O(number of live technologies + prerequisite/ingredient entries) Lua walk and response; its measured latency/bytes are **UNVERIFIED** [fle/env/tools/admin/save_research_state/server.lua:19-75; fle/env/tools/admin/save_research_state/client.py:10-54; fle/env/tools/controller.py:207-234]. The normal gym observation calls it each time [fle/env/gym_env/environment.py:319-320].

The PR414 header already gives current research name and percent each drain, and `q<name>` fires on `on_research_finished`. Neither full sync sends initial researched bits nor does the event stream enumerate all technologies; `TensorClient` only appends completion names and reports their count [fle/cluster/scenarios/open_world/observation_diff.lua:284-286,356-379,430-452; tests/benchmarks/benchmark_tensor_obs.py:301-314,424-435]. A full tech bitmask therefore needs a live snapshot at episode reset/cold attach, plus a deterministic name-to-bit schema and a policy for resets/research changes not represented by `q`. `fle.env.game_types.Technology` is a hard-coded enum and name lookup, but code does not establish it covers every installed game's `force.technologies`; **~256 slots, complete static enumeration, and cross-mod/scenario stability are UNVERIFIED** [fle/env/game_types.py:308-330,450-451; fle/env/tools/admin/save_research_state/server.lua:56-59].

## 6. Terrain and resources

The Lua is explicit: `emit("o" .. o.name .. ":" .. key .. ":" .. bucket)` with `bucket = math.floor(o.amount / RES_BUCKET)` and `RES_BUCKET = 100`; this is **per-resource-name tile data**, not a single ore channel. Water is a per-chunk 32×32 bitmask for `water`, `deepwater`, `water-green`, `deepwater-green`; no other tile categories are encoded [fle/cluster/scenarios/open_world/observation_diff.lua:43,48,187-223]. The benchmark client retains `self.ores["x:y"] = (name,bucket)` and chunk water masks, but its tensor update discards `name` into `C_ORE`. To make the 1-tile fine and 4-tile coarse windows, slice/reaggregate those persistent tile records by the header player position, preserving resource type and choosing count/presence/bucket normalization. These V0 grids and an explicit **known/generated tile mask** are **MISSING**; absence of a chunk record must not be mistaken for known dry/ore-free land [tests/benchmarks/benchmark_tiered_obs.py:17-23,57-85; tests/benchmarks/benchmark_tensor_obs.py:361-380,470-498; fle/cluster/scenarios/open_world/observation_diff.lua:356-379].

`get_resource_patch(resource, position, radius=30)` is a **separate tool query**. For ore it finds a matching resource near the position, recursively flood-fills neighboring same-name resource entities with one `find_entities_filtered` per visited tile, sums exact `entity.amount`, and returns only patch `bounding_box` and total `size`, not a tile raster. For water it queries only name `water` and returns a box/tile count. It also clears/adds render annotations. Cost is one RCON round trip plus O(patch tiles and neighbor searches) Lua work, measured wall time **UNVERIFIED**; it is not suitable as a per-cell, per-step grid source [fle/env/tools/agent/get_resource_patch/client.py:12-29,60-64; fle/env/tools/agent/get_resource_patch/server.lua:6-15,27-46,70-104].

Initial chunk events, later `on_chunk_generated`, and the terrain full sync provide enough records to maintain a persistent client-side map **of generated chunks** and slice egocentrically; the live test checks newly generated chunks reach the client. The stream does not itself generate or reveal unexplored chunks. Ore amounts are bucketed and only revisited four resource chunks per 47-tick pass, so exact current amounts and freshness under a large map are **UNVERIFIED** [fle/cluster/scenarios/open_world/observation_diff.lua:244-248,330-352,455-473; tests/observation_diff/test_tiered_protocol.py:254-260].
